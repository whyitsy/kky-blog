# 02 · CI/CD 实践

## 1. CI/CD 到底是什么

### 1.1 先把术语拆开

| 缩写 | 全称 | 人话 |
|---|---|---|
| **CI** | Continuous Integration | 代码**频繁合回主干**，且每次合并都**立刻由机器验证**没坏 |
| **CD** | Continuous Delivery | 验证通过后**自动产出随时能上线的包**，但"上线"由人点 |
| **CD** | Continuous Deployment | 验证通过后**自动上线**，没有人点 |

### 1.2 一个必须纠正的误解

> ❌ 「CI 就是自动跑测试。」

**CI 的第一个关键词是"集成"（Integration），不是"测试"。** 这个词来自 1990 年代的极限编程（XP），
针对的是**集成地狱**：各人在各自分支上开发几周，等到合并那天几百个冲突一起爆发、没人知道是谁弄坏的。
解法是两条：**频繁合并**（至少每天一次，让冲突小到当场能解决）+ **每次合并都自动验证**。

> **CI ≠ 有测试。CI = 频繁集成 + 自动验证。** 一个没有测试但有自动构建的项目，也是有 CI 的。

### 1.3 一次完整的流程

**你写代码 → `git push` 触发 → 机器接手（①拉代码 ②还原依赖 ③编译 ④格式/静态检查 ⑤测试
⑥安全扫描 ⑦产出制品）→ 通过 ✅ / 失败 ❌ → 人评审合并 → 部署。**

**①~⑦ 是 CI，部署那一段是 CD。**

### 1.4 关键词：清室验证（Clean-room Verification）

> **在一台"什么都没装过、跟你的开发机毫无关系"的机器上，把项目从零构建一遍。**

最重要的四个字是**"什么都没装过"**。你的开发机上装过什么，你自己都不完全记得：某个 SDK、
某个环境变量、某个手工编译的镜像、某个 PATH 里的工具——它们**不会出现在别人的机器上，
也不会出现在服务器上**。**凡是"只在你机器上能跑"的东西，CI 会立刻把它暴露出来。**

## 2. 一条流水线的通用结构

### 2.1 标准阶段

| 阶段 | 做什么 | 失败意味着 | 耗时量级 |
|---|---|---|---|
| **触发 / 检出** | push、PR、定时、手动；拉代码 | 几乎不会失败 | 秒 |
| **还原依赖** | NuGet / npm 下载 | 依赖被删、版本冲突、网络问题 | **最慢**（可缓存） |
| **编译** | `dotnet build` / `vite build` | 语法/类型错误 | 分钟 |
| **静态检查** | 格式、lint、分析器 | 代码风格不达标 | 秒~分钟 |
| **测试** | 单元 / 集成 / E2E | 行为不符合预期 | 分钟 |
| **安全扫描** | 依赖漏洞、密钥泄漏 | 用了有已知漏洞的包 | 秒~分钟 |
| **打包 / 发布**（CD） | 产出制品；推镜像 / 重启服务 | 打包配置错 | 分钟 |

### 2.2 两条铁律

> **铁律一：主干永远是可构建的（Green Main）。** 任何时刻 `main` 上最新提交都必须能通过全部流水线。
> 如果它红了，**修它是全项目最高优先级**——因为其他人（包括未来的你）会基于它继续开发。

> **铁律二：失败必须阻断合并（Required Status Checks）。** 光"跑流水线"是不够的：
> 如果红了还能合并，CI 就**只是多跑了一遍**。必须在托管平台上开启**分支保护**，
> 把 CI 设为合并的必要条件。

### 2.3 快反馈原则（Fail Fast）

流水线的价值与「你多久知道结果」成反比。

| 做法 | 效果 |
|---|---|
| ✅ 快的任务排前面（格式 → 编译 → 单元 → 集成） | 最常见的问题最快报出来 |
| ✅ 各任务**并行**（前后端互不依赖）+ `fail-fast`（第一个失败就中止同组） | 总时长 ≈ 最慢的那条，且早反馈、省算力 |
| ❌ 所有检查串成一条长链 | 第 8 步失败，前 7 步的时间全白花。应该编写并行任务。 |

### 2.4 缓存：CI 性能的关键

CI 机器**每次都是全新的**，所以每次都要重新下载全部依赖——这是 CI 里最大的时间开销。
**核心思想**：把「依赖清单文件的哈希」作为缓存键的一部分；清单没变 → 命中，清单变了 → 自动换新。

多次CI之间缓存命中且未变可复用。

| 生态 | 缓存什么 | 缓存键怎么写 |
|---|---|---|
| .NET | `~/.nuget/packages` | 按 `**/*.csproj` 的哈希 |
| Node | npm 缓存 | 按 `package-lock.json` 的哈希 |
| Docker | 镜像层 | 按 Dockerfile 的哈希 |

## 3. 本项目的流水线

### 3.1 四个并行检查，加一条发布/部署链

`.github/workflows/ci.yml` 里四个检查作业**互不依赖**（并行）：

| 作业 | 包含步骤 | 需要外部服务 | 耗时量级 |
|---|---|---|---|
| `hygiene`（卫生检查） | 检出 → 行尾 CRLF 检查 | 无 | **秒级** |
| `security`（依赖安全扫描） | 检出 → restore → NuGet 扫描 → `npm audit` → 写作业摘要 | 无 | 约 1 分钟 |
| `frontend`（类型检查 + 构建） | 检出 → `npm ci` → `vue-tsc` → `vite build` | 无 | 十几秒 |
| `backend`（构建 + 测试 + 覆盖率） | 检出 → restore → **格式检查** → 编译 → 起 PG/Redis → 校验 zhparser → 测试 → 覆盖率 | **PG + Redis** | 约 2 分钟 |

后两个作业依次串成一条链（`security` 只报告不阻断，刻意不在链上）：

| 作业 | 何时跑 | 做什么 |
|---|---|---|
| `publish`（发布镜像） | 合并进 `main`、或推 `v*` tag，**且三个检查全绿** | 构建 `webapi` / `nginx` 推到 GHCR，tag = 那次提交的 sha |
| `deploy`（自动部署） | `publish` 成功之后 | 同步 compose / 部署脚本 → SSH 执行 `deploy.sh update <sha>` → **从公网**核对 `/api/version` 报出的就是这次 sha |

> ⚠️ **两道接缝都在 `needs` 上，而且都不显眼**：
> ① `publish` 若不写 `needs: [hygiene, frontend, backend]`，它就与检查作业**并行** —— 测试红着照样推镜像；
> ② `deploy` 只 `needs: publish` 之所以够，是因为 publish 已经卡在检查之后；
>    谁把 publish 的 `needs` 拿掉，deploy 就跟着一起失守。
> 「门禁」和「自动化」最典型的接缝就在这里，而且它不会以任何显眼的方式报错。

> ⚠️ **"部署成功"的判据不由 SSH 的退出码给**：`deploy` 的最后一步从公网拉
> `https://<站点>/api/version`，断言里面的 commit 就是这次部署的 sha。Caddy / nginx / 应用缓存
> 任何一层没换，SSH 那边都看不出来 —— 这是「失效哨兵」用在部署上的样子：失败会红，不会静默。

> **为什么 `hygiene` 单独拆出来**：它最快也最容易失败（格式问题最常见），排前面能让大部分小问题
>在 1 分钟内反馈。**为什么依赖扫描也单独拆一个作业**：它回答的是另一个问题——其余作业问
> "我写的代码对不对"，它问"我依赖的代码还安全吗"，后者会在你一行代码都没改的情况下变坏。

### 3.2 触发条件

真实触发条件是 `push: [main]` + `pull_request: [main]` + `workflow_dispatch`（手动），
其中 `push` 还带 `tags: ["v*"]` —— 推版本 tag 同样触发（那正是"发布"这个动作）。**往功能分支
单独 push 不会触发流水线**——「我推了分支，怎么 Actions 里什么都没有」不是故障，是设计；代价是
功能分支在**开 PR 之前拿不到任何 CI 反馈**。

> ⚠️ **手动触发只跑那四个检查作业**：不推镜像、不部署。理由同上 —— `workflow_dispatch` 的 ref
> 可以是任意分支，让它发布或部署就等于"把功能分支发到生产"。
> 所以手动触发的用途是**重跑排查**，而不是"发布/上线"。

| 概念 | GitHub Actions | GitLab CI |
|---|---|---|
| 流水线定义 / 一组任务 | `.github/workflows/*.yml` / `jobs.<name>` | `.gitlab-ci.yml` / `<stage>` + `script` |
| 运行环境 / 依赖缓存 | `runs-on: ubuntu-latest` / `actions/cache@v4` | 由 Runner 决定（`tags`） / `cache:` |
| 制品 / 密钥 / 服务容器 | `upload-artifact@v4` / `secrets.NAME` / `services:` | `artifacts:` / CI/CD Variables / `services:` |

## 4. 质量门禁（Gate）

门禁 = **CI 里那些"不过就不许合并"的检查**。这一节回答"该设哪些、标准是什么"。

### 4.1 测试金字塔，以及本项目的实际形状

**测试金字塔**（Mike Cohn 提出，Martin Fowler 推广）：越往上的测试跑得越慢、越容易随机失败、
定位越难，所以**数量应该越少**——不是因为它们不重要，而是因为**单位成本高**。**本项目的实际
形状是一个"倒金字塔"**：集成测试（真实 HTTP + 真实 PostgreSQL）比纯单元测试还多（当前数量由
代码决定，实测见 CI 作业摘要）。

### 4.2 覆盖率

**该看的指标**（价值从高到低）：**关键路径是否被覆盖**（权限校验、计数/状态转换）→
**变更覆盖率**（本次改动的新代码测了多少，比整体数字有用得多）→ **趋势**（方向有意义，绝对值
无意义）→ **分支覆盖 vs 行覆盖**（行覆盖把 `if` 的假分支也算作已覆盖）。

本项目关注点在关键路径（授权策略、乐观锁、草稿可见性），并把覆盖率
**写进 CI 作业摘要**：制品要下载才看得到，摘要打开 PR 就在眼前。

### 4.3 覆盖率的三个问题

**一、不排除生成代码，这个数字根本没有意义。** 五个 EF Core 生成的迁移与模型快照文件占了
`Blog.Infrastructure` 全部行数的**约七成**。迁移代码"被执行过"（集成测试一跑必然执行它们），但
**它一行都不代表被测过**——它只是把分母和分子同时往上抬，把"哪部分业务代码是裸奔的"这个真正
该看的问题淹没掉；`Blog.WebApi` 里编译器生成的 OpenAPI XML 注释支持代码覆盖率恒为 0%。于是有了
`Blog.Backend/coverage.runsettings`，排除 `**/Persistence/Migrations/*.cs`、
`**/*ModelSnapshot.cs`、`**/obj/**/*.cs`。

**二、真实基线会暴露"裸奔点"（这才是有用的部分）。** 排除生成代码后立刻能看出一批**行覆盖极低
甚至为 0 的位置**：限流中间件、健康检查、集合与分类/标签的**写**路径（新增之外的更新 / 删除 /
排序）。按风险排序第一个该补的是**限流中间件**——它是一道**安全控制**，而集成测试里
`RateLimit:Enabled = false` 把它关掉了，所以「防 `X-Forwarded-For` 绕过」的验证目前只在手工跑。
**下一步该补什么，这张表就是答案**（具体数字随代码变化，以 CI 作业摘要为准）。

> ⚠️ **这张清单本身被校准过一次，值得当作方法论的例子**：它原先写的是「分类/标签的**读**路径」，
> 但读路径（`GET /api/categories`、`GET /api/tags`）在公开读接口测试里是覆盖到的；0% 的是同两个
> Service 的 `Create` / `Update` / `Delete` —— 那是**写**路径。起因是压缩文档时把"整个 Service 类
> 的百分比"误标成了"业务读路径"。同理，「内存缓存实现」一项也已不成立：`CurrentUserCacheTests`
> 用的是**真实**的 `MemoryCacheService` 而不是 mock，命中 / 回源 / 失效三条路径都会执行到。
>
> **教训**：这类清单必须写到「哪个类的哪个方法」。写"读路径""缓存实现"这种笼统名词，
> 错了从字面上根本看不出来 —— 而它会一路被当成"下一步该补什么"的依据。

**三、覆盖率会「静默消失」。** 原来用 `--collect:"XPlat Code Coverage"`；改用
`--settings coverage.runsettings` 之后，**覆盖率就依赖那个文件了**。它被删除、改名，或
`--settings` 参数被顺手去掉，`dotnet test` 都会**照常变绿**、制品照常上传（只是里面没有覆盖率
文件），而你会以为"覆盖率一直在正常收集"。所以 CI 里那一步兼作**哨兵**：找不到
`coverage.cobertura.xml` 时**直接报错**。

### 4.4 依赖安全扫描：为什么「只报告不阻断」

| 扫描对象 | 命令 / 工具 |
|---|---|
| NuGet **含传递依赖** | `dotnet list package --vulnerable --include-transitive` ⚠️ 漏洞通常藏在**传递依赖**里 |
| npm | `npm audit --registry=https://registry.npmjs.org` ⚠️ **源必须显式指定** |
| 密钥泄漏 / 自动化 | 平台的 secret scanning；**Dependabot**（`nuget` + `npm` + `github-actions`） |

> ⚠️ **一、这个项目早就在扫，只是没人看得见**：NuGet Audit 从 .NET 8 SDK 起**默认开启**，
> `dotnet restore` / `dotnet build` 会打出 `NU1903` 警告——不会让流水线变红，也没有人看见。
> 缺口的准确描述不是"完全没做"，而是"信息一直在输出，却没有任何机制让它被看见"。
>
> ⚠️ **二、危险之处在于组合条件**：`npm audit` 在默认镜像源下返回 `404 [NOT_IMPLEMENTED]` 且
> **非 0 退出**，而作业是 `continue-on-error` → **「审计没跑成」和「审计跑了、没发现漏洞」在
> 页面上长得一模一样**。所以 CI 里加了一道显式检查：输出里必须出现 `found N vulnerabilities`
> （N 可以是 0），没有就报错，而不是当成"干净"。同理，**抑制某个包的升级 PR 时只写
> `dependency-name` 的 ignore 规则会被展开成 `>= 0`，并同时作用于安全更新通道**——必须显式写
> `update-types`。

**为什么只报告不阻断**：先只看结果；等结果稳定、确认"报出来的都会修"，再改成阻断。

### 4.5 一份可执行的门禁清单

每条都给出**具体的失败条件**，否则门禁形同虚设。

| 顺序 | 门禁 | 失败条件 | 状态 |
|---|---|---|---|
| 1 | 后端编译 | `dotnet build` 非 0 退出 | ✅ |
| 2 | 后端测试 | 任一测试失败；**0 个测试被执行也算失败** | ✅ |
| 3 | 前端类型检查 | `vue-tsc` 报错 | ✅ |
| 4 | 前端构建 | `vite build` 失败 | ✅ |
| 5 | 行尾检查 | 存在 `w/crlf` | ✅ |
| 6 | 分支保护开启 | 上面任一失败则**禁止合并**（直推同样被拒） | ✅ |
| 7 | C# 格式（whitespace） | `dotnet format … --verify-no-changes` 报差异 | ✅ **只查空白/行尾，不查 analyzer**（一次性把 analyzer 建议变成门禁 = 大量改动 + 长期噪音） |
| 8 | 覆盖率 | 不阻断、**不设阈值**；**报告丢失则报错** | ✅ |
| 9 | 依赖漏洞扫描 | 有高危 CVE（**先只报告不阻断**） | ✅ |
| 10 | 前端 ESLint | lint 报错（**需先配置并清理存量**） | ❌ |

### 4.6 分支保护怎么验（正反两个方向都要验）

**配好了和没配好，界面看起来差不多**，所以必须做**反向验证**——用「故意失败」的提交去撞门禁。

| 方向 | 手段 | 预期 |
|---|---|---|
| **PR 合并**被拦 | 开一个含**故意失败测试**的 PR | 必需检查变红，**Merge 按钮变灰不可点** |
| **直推 main**（检查失败的分支） | `git push origin <bad>:main` | 被拒：`GH006: Protected branch update failed` |
| **直推 main**（正常但没跑过检查的分支） | 同上 | 被拒：`Changes must be made through a pull request.` |

## 5. CD：从"能构建"到"能上线"

| | CI | CD |
|---|---|---|
| 问题 / 产物 / 失败后果 | "这份代码是对的吗？" / 一个**结论** / 开发者看到红叉 | "怎么把它安全地放上服务器？" / 一个**制品** / **线上用户受影响**，所以要谨慎 |

后端制品是 `dotnet publish` 输出或容器镜像，前端是 `vite build` 的 `dist/`，跟同一个 git tag；
数据库镜像固定 `:18`。 **镜像绝不要只用 `:latest`**（会移动的标签，出事时说不清线上跑的是哪一版），
正确做法是 `日期 + 提交短哈希`。

**本项目的形态是「合并即上线」**：`publish` 把镜像推到 GHCR（tag 就是那次提交的 sha），`deploy`
紧接着在三个检查作业全绿、镜像推送成功之后 SSH 到服务器执行 `tools/deploy/deploy.sh update <sha>` —— 脚本**先 pull
成功再改 `.env`**，最后 `docker inspect` 断言容器**真的**在跑新镜像，而不是只看命令退出码。
合并进 `main` 与推 `v*` tag 都会触发；手动触发不会（理由见 §3.2）。

> ⚠️ **自动化的代价要写在明处**：CI 只证明"测试全绿"，不证明"这个改动是对的"。合并即上线意味着
> **测试覆盖不到的地方没有第二道闸门**。本项目的对策不是假装 CI 能兜住一切，而是把不可逆的动作
> 变少：数据库迁移做成向前兼容、回滚写成一条命令（[05-运维与部署手册](../docs/05-运维与部署手册.md) §8.9），
> 并且**首次部署仍然是人工走一遍的**（服务器上那时还没有 compose 与 `.env`）。

### 5.1 密钥管理

密钥**绝不进仓库**：`appsettings.json` 里**没有** `Jwt:SigningKey`，缺失或长度不足时**应用直接
拒绝启动**；开发期用 `dotnet user-secrets`，运行期用环境变量 `Jwt__SigningKey`（双下划线 = 配置的
`:`），CI/CD 期用平台的加密变量。

> ⚠️ **轮换密钥对本项目是一个真问题**：本项目**只发 Access Token、没有 Refresh Token**
> （刻意的技术决策，见 [archive/决策记录.md](../archive/决策记录.md)），所以**一旦换了
> `Jwt:SigningKey`，所有已登录用户的 token 立即失效**。个人博客上可接受（提前公告即可）。

## 6. 坑清单

### 6.1 环境变量在 CI 里的写法

.NET 的配置系统用**双下划线**表示层级（`Jwt__SigningKey` 还必须 ≥ 32 字节，否则应用拒绝启动），这在 YAML 里极易写错：

| 想配置的键 | 环境变量写法 | 常见错误 |
|---|---|---|
| `Jwt:SigningKey` | `Jwt__SigningKey` | ❌ 写成 `Jwt:SigningKey`（YAML 里会被当字符串，应用读不到） |
| `ConnectionStrings:DefaultConnection` | `ConnectionStrings__DefaultConnection` | 同上 |
| `Cache:Provider` | `Cache__Provider` | 同上 |

### 6.2 测试夹具：环境变量优先、文件回退

```
BlogApiFactory.ResolveConnectionString()
  → ① 读环境变量 BLOG_CONNECTION（与设计期工厂 BlogDbContextFactory 同名同义）
  → ② 没有才回退：沿目录向上找 Blog.Backend.slnx（定位仓库根）
       → 读取 appsettings.Development.json 的连接串 → 只把 Database 换成随机测试库名
```

| 推论 | 说明 |
|---|---|
| CI 不再依赖"开发机那份配置恰好一致" | ✅ CI 显式传 `BLOG_CONNECTION`，容器起在哪、测试就连哪 |
| 本地开发零改动 | ✅ 不设这个变量时行为与从前完全一样（回退到文件） |
| 想连别的 PG（另一台机器 / 别的端口 / 别的凭证） | ✅ `BLOG_CONNECTION='Host=…;Username=…;Password=…;' dotnet test` |
| Redis 地址仍是「读文件 + 回退 `localhost:6379`」 | ⚠️ 夹具会把它改写成随机 `defaultDatabase` 做隔离，但没有对应的环境变量 |

> ⚠️ 这类"从文件读配置"的夹具，问题不在**读文件**，而在于**没有覆盖入口**：环境一旦不同，
> 失败信息会指向完全无关的地方（`The server has not been started or no web application was configured`，
> 见 [05-运维与部署手册](../docs/05-运维与部署手册.md) §4.2），于是你会去查代码而不是查环境。
