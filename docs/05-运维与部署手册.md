### 1.1 ⚠️ 盘符路径：是 `/mnt/c`，不是 `/c`

Windows 盘在本环境的挂载点是 **`/mnt/c`、`/mnt/d`**。`/c` 不存在：

```bash
/mnt/c/Windows/System32/taskkill.exe /F /IM Blog.WebApi.exe   # ✅
/c/Windows/System32/taskkill.exe /F /IM Blog.WebApi.exe       # ❌ No such file or directory
```

历史文档里出现过 `/c/...` 的写法，那是错的 —— 症状是"命令明明抄对了却报文件找不到"，
很容易被误判成"Windows 工具没装"。

## 2. 环境陷阱清单

这一节是本项目**耗时最多的部分**，全部是实测踩出来的。
标题里的 ✅ / ⚠️ 表示**本条在 2026-09-14 的复核结论**。

### 2.1 ✅ WSL 只能连到「Docker 发布的端口」，连不上 Windows 原生进程

WSL2 有**自己的**回环网络，和 Windows 的不是同一个网络栈。能否连通取决于**端口是谁发布的**：

| 监听者 | 例子 | WSL 里 `127.0.0.1:<port>` | 实测（2026-09-14） |
|---|---|---|---|
| **Windows 原生进程** | Kestrel `5131`、Vite `5173` | ❌ **不可达** | 实测返回 `000`（连接失败） |
| **Docker 发布的端口** | Nginx `8080`、开发用的 `pgsql` `5432` / `redis` `6379` | ✅ **可达** | `8080/health` → `200 Healthy`；`5432` 可连接 |
| **Compose 内网服务** | `docker compose` 的 `pgsql` / `redis`（刻意不发布） | ❌ 不可达 | 只有 `nginx` 发布了 `8080` |

**解法**：连 Docker 整栈（`8080`）直接在 WSL 里 `curl`；连 Windows 原生进程
（`5131` / `5173`）走 Windows 侧的程序：

```bash
/mnt/c/Windows/System32/curl.exe -s --noproxy '*' http://localhost:5131/api/site/config
```

> ⚠️ **`--noproxy` 与 `*` 必须分成两个参数。** 写成 `--noproxy=*` 时 curl 直接报
> `option --noproxy=*: is unknown` —— 实测即使当前目录**没有任何**可被展开的文件也照样报错。

### 2.2 ✅ 环境变量不生效 / WSL 的 node 不能用于前端

- **`ASPNETCORE_ENVIRONMENT` 不生效** → 启动 `Blog.WebApi.exe` 时报
  `The ConnectionString property has not been initialized`。根因：通过 WSL 启动 Windows exe 时，
  WSL 的环境变量不会传递给 Windows 进程。**解法**：用**命令行参数**指定环境，而不是环境变量：

  ```bash
  ./Blog.WebApi.exe --urls http://localhost:5131 --environment Development
  ```

- **`npx vite` 报 `Cannot find native binding`** → WSL 的 node 缺少
  `@rolldown/binding-linux-x64-gnu` 原生绑定（依赖在 Windows 侧安装）。**解法**：一律用 Windows 的 node。

  ```bash
  "/mnt/c/Program Files/nodejs/node.exe" ./node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5173
  cmd.exe /c "npx vue-tsc -b --force"     # 类型检查
  cmd.exe /c "npx vite build"             # 构建
  ```

### 2.3 ✅ dotnet 构建被文件占用

**现象**：`dotnet build` 报 `MSB3027` / `MSB3021`（无法复制 DLL）。
**根因**：运行中的 `Blog.WebApi.exe` 锁住了输出目录的 DLL。**解法**：

```bash
/mnt/c/Windows/System32/taskkill.exe /F /IM Blog.WebApi.exe
```

> `Blog.WebApi.csproj` 里有一个 `KillRunningBlogWebApi` MSBuild Target
> （`BeforeTargets="Build"`，`Condition="'$(OS)' == 'Windows_NT'"`），构建前会自动 `taskkill`。
>
> ⚠️ **但实测它拦不住（2026-09-14）**：构建仍以 `MSB3027` / `MSB3021` 失败了 10 次重试，
> 报错里明确写着 `文件被"Blog.WebApi (15616)"锁定`。所以**别指望它**，手工再杀一次。
> 另一个观测细节：`taskkill` 报"成功"后 `tasklist` **短时间内仍会列出**那个 PID，等 2~3 秒再查。

### 2.4 ⚠️ 后端进程随 Bash 会话消失 —— **根因不成立，症状另有成因**

**现象**：前端突然全部 `ECONNREFUSED`，但刚才明明启动过后端。

**原文档的根因**（"用 `&` / `nohup ... &` 启动的进程在 Bash 会话结束后被系统清理"）
**在 2026-09-14 被实测推翻**：`nohup sleep 45 &`、`sleep 60 &`（不加 `nohup`）、
`nohup PING.EXE -n 60 &`（Windows 原生进程）三者在**下一次全新 bash 调用**里**全部仍存活** ——
**后台进程不会因为"发起它的那个 bash 调用结束"而被清理。**

**真实成因按可能性排序**：① **进程自己退出了**（最可能：启动时要执行数据库迁移，
连不上 PG / 缺 `Jwt:SigningKey` 或连接串时会**直接崩**，日志里有原因）；
② **被构建顺手杀掉**（`dotnet build` 的 Target 会 `taskkill`，见 §2.3）；
③ 宿主机/容器重启（Docker Desktop 重启会带走 compose 栈，但不影响 Windows 侧进程）。

**解法（建议保留）**：仍然**推荐**用工具的 `run_in_background=true` 启动后端与前端 ——
不是因为"不加就会被清理"，而是因为它让**进程句柄归工具管**：退出状态、stdout/stderr
都能追。**真正的排查顺序**：

```bash
/mnt/c/Windows/System32/tasklist.exe /FI "IMAGENAME eq Blog.WebApi.exe"   # 1) 进程还在不在
tail -50 Blog.Backend/Blog.WebApi/logs/blog-$(date +%Y%m%d).log           # 2) 不在了 → 看退出前写了什么
/mnt/c/Windows/System32/curl.exe -s -o /dev/null -w "%{http_code}\n" \
  --noproxy '*' http://localhost:5131/                                    # 3) 还在 → 端口通不通
```

### 2.5 ⚠️ dotnet 不在 PATH（附带"出现 `path1` 时"的备用处方）

**现象**：`dotnet: command not found`（实测确认）。**解法**：用绝对路径。

```bash
"/mnt/c/Program Files/dotnet/dotnet.exe" build Blog.Backend.slnx
```

**若还报 NuGet 恢复失败**（`ArgumentNullException: path1`，来自
`NuGetEnvironment.CalculateFolderPath`）：说明当前 bash 会话缺少 Windows 环境变量。
可以在命令前**内联补齐**，不需要任何包装脚本文件：

```bash
cd Blog.Backend
env APPDATA="C:\\Users\\<用户名>\\AppData\\Roaming" LOCALAPPDATA="C:\\Users\\<用户名>\\AppData\\Local" \
  USERPROFILE="C:\\Users\\<用户名>" ProgramData="C:\\ProgramData" ProgramFiles="C:\\Program Files" \
  "ProgramFiles(x86)=C:\\Program Files (x86)" ProgramW6432="C:\\Program Files" OS="Windows_NT" \
  "/mnt/c/Program Files/dotnet/dotnet.exe" build Blog.Backend.slnx
```

> 把用户名换成你的（本机是 `kky`）。这段内联 `env ...` 与曾经的包装脚本
> `/mnt/d/tmpbuild/dn.sh` **完全等价** —— 但那个目录**已经不存在了**，不要再引用它，
> 也不建议再造一个仓库外的脚本（§7.1 的教训：仓库外的文件不是项目资产）。
> 真的需要更全的变量集时，把 `CommonProgramFiles` / `ALLUSERSPROFILE` 等一并补上即可。
>
> ⚠️ **这条不是每次都会触发**：实测（2026-09-14）当前会话里 `APPDATA` / `LOCALAPPDATA` /
> `USERPROFILE` / `ProgramData` **全部未设置**，但 `dotnet build` 与 `dotnet restore` 都成功。
> 所以把它当**备用处方**，而不是每次构建的必需前置。

### 2.6 ✅ 全文检索报配置不存在 / Chrome 无头截图挂住

- **`ERROR: text search configuration "chinese" does not exist`**：连到了**不含 zhparser 的
  PostgreSQL**（通常是官方 `postgres` 镜像）。确认并重建：

  ```bash
  docker inspect pgsql --format '{{.Config.Image}}'      # 期望 mixdeve/postgres-zhparser:18
  # 若不是，按 deploy/README.md §4 换回社区镜像（数据卷沿用，不丢数据）
  ```

  容器重建不会再有这个问题：zhparser 已在镜像内，`chinese` 检索配置由
  **EF 迁移**负责创建与补齐（`20260910205225_AddAuthCollectionsAndFts` 建配置，
  `20260918174440_EnsureChineseConfigTokenMappings` 补齐 j,q 映射），
  不再依赖 `docker-entrypoint-initdb.d` 下的脚本。
  权威来源见 [02-架构与数据模型.md](./02-架构与数据模型.md) §9。

- **`chrome.exe --headless ... --screenshot=...` 不退出**：先清残留进程，并加
  `--virtual-time-budget`：

  ```bash
  /mnt/c/Windows/System32/taskkill.exe /F /IM chrome.exe
  ```

## 3. 日常启动与停止

### 3.1 启动前检查

```bash
docker ps --format "table {{.Names}}\t{{.Status}}"    # 期望 pgsql 与 redis 都是 Up
```

### 3.2 启动后端

在仓库根目录执行，**用 `run_in_background=true`**：

```bash
cd Blog.Backend/Blog.WebApi/bin/Debug/net10.0 && \
env -u HTTP_PROXY -u http_proxy -u HTTPS_PROXY -u https_proxy \
./Blog.WebApi.exe --urls http://localhost:5131 --environment Development
```

- `env -u ...` 清除代理变量：环境里有大小写重复的代理变量，
  用 `Start-Process` 时会因 .NET 字典重复键而报错
- 启动时会**自动应用迁移**（`dbContext.Database.Migrate()`）

> 若 `bin/Debug/net10.0` 不存在，先构建一次（§4.1）。

### 3.3 启动前端

在 `Blog.FrontEnd/` 目录执行（实测约 0.4 秒起好，Vite 8）：

```bash
"/mnt/c/Program Files/nodejs/node.exe" ./node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5173
```

### 3.4 停止

```bash
/mnt/c/Windows/System32/taskkill.exe /F /IM Blog.WebApi.exe   # 后端
# 前端 dev server：结束对应后台任务即可
```

### 4.2 测试

```bash
cd Blog.Backend
"/mnt/c/Program Files/dotnet/dotnet.exe" test Blog.Tests/Blog.Tests.csproj

# 只跑某一组
"/mnt/c/Program Files/dotnet/dotnet.exe" test Blog.Tests/Blog.Tests.csproj \
  --filter "FullyQualifiedName~AuthorizationMatrixTests"

# 顺带出覆盖率报告（与 CI 完全一致的方式）
"/mnt/c/Program Files/dotnet/dotnet.exe" test Blog.Tests/Blog.Tests.csproj \
  --settings coverage.runsettings
```

> ⚠️ 覆盖率必须带 `--settings coverage.runsettings`，否则报告里会混进 **EF 迁移与源生成代码**，
> 数字明显虚高（`Blog.Infrastructure` 尤其明显）。排除前后差多少、为什么方向是
> "行覆盖率降低、分支覆盖率升高"，见 `Blog.Backend/coverage.runsettings` 的文件头注释。
> 报告产出在 `Blog.Tests/TestResults/<guid>/coverage.cobertura.xml`（已被 gitignore）。

**测试规模以运行输出为准**（`dotnet test` 末行的 `总计: N`）——
**不要在任何文档里写死总数**，那个数字每次加测试就会过期，本仓库已因此反复返工。
可写死的是**测试文件与它们负责什么**：

| 层 | 文件 | 覆盖 |
|---|---|---|
| 集成 | `AuthorizationMatrixTests` / `DraftProtectionTests` / `OptimisticLockTests` | 权限矩阵（匿名/Author/Admin × 写/读/上传）；草稿保护（不可读返回 404 而非 403）；乐观锁 409、非法版本 4001 |
| 集成 | `MediaUrlValidationTests` | **媒体安全**：地址白名单的端点级校验（绕开前端直接打 HTTP）+ **上传 SVG 必须被拒** + **上传错误必须是 400/413 而不是 200** |
| 集成 | `FieldLengthValidationTests` / `UnifiedErrorResponseTests` | 字段长度端点级校验（摘要/简介/社交链接边界，超长**不能返回 5xx**）；统一错误响应形状 |
| 单元 | `PostServiceTests` / `MediaPathTests` / `FieldLimitsTests` | Service 层业务规则（入参/归属/版本/摘要/发布幂等）；**媒体地址判定**（攻击样本 + 合法样本）；**字段常量护栏**（EF 元数据反查 `HasMaxLength` 与 `FieldLimits` 逐个比对） |
| 图片 | `ImageSharpOptimizerTests` | 图片转 WebP 的边界行为（一个扩展名一个用例） |

#### ⚠️ 集成测试的环境要求与行为

集成测试会**真实启动宿主 + 连真实 PostgreSQL**（`WebApplicationFactory`），因此：

| 事项 | 说明 |
|---|---|
| 需要 PG 在跑 | 测试库是 `blog_stage2_test_{8位随机}`，每次运行**自动创建、结束自动删除**，不污染开发库 |
| **连哪个 PG 由环境变量说了算** | 夹具按「环境变量 `BLOG_CONNECTION` → 回退 `Blog.WebApi/appsettings.Development.json`」解析，**只替换库名**（主机 / 端口 / 凭证照用）。与设计期工厂 `BlogDbContextFactory` 同名同义，CI 就是在测试步骤显式传它 —— 所以本机把 PG 装在别处时，不必改仓库里的配置文件：<br>`BLOG_CONNECTION='Host=…;Port=…;Username=…;Password=…;' dotnet test Blog.Tests/Blog.Tests.csproj` |
| 需要 `zhparser` | ⚠️ **需要的是「镜像里有这个扩展」，而不是「测试帮你建好」**：测试夹具只负责 `CREATE DATABASE`（EF 的 `Migrate()` 不建库），**扩展与 `chinese` 检索配置由迁移自己创建**。所以要用带 zhparser 的镜像 `mixdeve/postgres-zhparser:18` |
| **关闭了限流** | 测试连发大量请求，且限流桶存在 **Redis** 里、是跨运行共享的外部状态，会污染后续运行 |
| Redis 地址仍读配置文件 | 夹具把 `Cache:RedisConnection` 换成一个随机 `defaultDatabase` 做隔离；没有对应的环境变量 |
| 需要先停后端 | `dotnet build` 会因运行中的 `Blog.WebApi.exe` 锁文件而失败（先 `taskkill`，见 §2.3） |

#### 为什么测试工程要用 `GenerateProgramFile=false`

`Blog.Tests` 引用 `Blog.WebApi` 后，SDK 仍会为 Exe 类工程自动生成一个空的 internal `Program`，
它与 WebApi 顶层语句生成的 `Program` **同名**，导致 `WebApplicationFactory<Program>`
解析到错误的类型，报 **"The server has not been started or no web application was configured"**。
因此测试工程关掉自动生成，并由 `TestEntryPoint.cs` 提供自己的入口点。

> ⚠️ **排查提示**：`WebApplicationFactory` 会把宿主启动的真实异常**完全吞掉**，只留上面那句话。
> 若集成测试报这个错，**不要相信它** —— 真正的失败原因通常是
> 「库不存在 / 缺扩展 / 连不上 / 依赖版本冲突」，需要绕过工厂直接构造宿主或临时打日志才能看到。

### 4.4 数据库迁移

`dotnet-ef` 版本固定在 `Blog.Backend/dotnet-tools.json`（`10.0.11`）。

```bash
cd Blog.Backend
# 生成迁移（在 Blog.Infrastructure 项目上操作）
"/mnt/c/Program Files/dotnet/dotnet.exe" ef migrations add <迁移名> \
  --project Blog.Infrastructure --startup-project Blog.WebApi
# 应用迁移（通常不需要：应用启动时会自动执行）
"/mnt/c/Program Files/dotnet/dotnet.exe" ef database update \
  --project Blog.Infrastructure --startup-project Blog.WebApi
# 查看已应用的迁移
"/mnt/c/Program Files/dotnet/dotnet.exe" ef migrations list \
  --project Blog.Infrastructure --startup-project Blog.WebApi
```

| 坑 | 说明 | 正确做法 |
|---|---|---|
| 用 `--no-build` 生成迁移 | 会读到**旧的编译产物**，迁移生成不完整 | **不要加 `--no-build`** |
| 用 `migrations remove` 撤销未应用的迁移 | **不会回退模型快照**，残留不一致 | `git checkout -- Blog.Infrastructure/Persistence/Migrations/BlogDbContextModelSnapshot.cs` + 手工删迁移文件，然后重新 `add` |

> **迁移与宿主解耦**：`BlogDbContextFactory`（`IDesignTimeDbContextFactory`）
> 让 `dotnet ef` 不依赖 `Program.cs` 的启动配置 —— 即使应用因缺少 `Jwt:SigningKey`
> 而无法启动，依然可以生成迁移。

### 5.2 登录并带 token 调用受保护接口

```bash
TOKEN=$(/mnt/c/Windows/System32/curl.exe -s --noproxy '*' \
  -X POST http://localhost:5131/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@example.com","password":"Admin@12345"}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

  -H "Authorization: Bearer $TOKEN" \
  "http://localhost:5131/api/posts?includeUnpublished=true"
```

### 5.3 验证容器整栈（不需要 Windows curl）

`8080` 是 Docker 发布的端口，WSL 直连即可（§2.1）：

```bash
curl -s --noproxy '*' http://127.0.0.1:8080/health           # Healthy
curl -s --noproxy '*' http://127.0.0.1:8080/api/site/config # JSON
curl -i -s --noproxy '*' http://127.0.0.1:8080/post/<uuid>   # 200 + index.html（SPA fallback）
```

### 5.4 判断响应真伪

> ⚠️ 环境里某些工具的 localhost 请求**会被 mock 层拦截并返回伪造数据**，不能用于接口验证。
> **可靠判据**：查后端日志是否有对应请求记录。

```bash
tail -f Blog.Backend/Blog.WebApi/logs/blog-$(date +%Y%m%d).log
# 形如：2026-09-11 10:23:45.123 +08:00 [INF] HTTP GET /api/site/config 响应 200 耗时 12.3456 ms
```

> `docker compose exec pgsql psql -U kky -d blog_stage2`

## 7. 版本控制纪律

### 7.1 ⚠️ 提交前必须复核

```bash
git status --short
git show --stat HEAD
```

**本项目历史上多次发生"无关文件被误删/误加并混入提交"**，
以及"工作区 39 个文件仅因行尾 CRLF/LF 差异被整体纳入提交"。因此：

- 用 `git add -A` / `git add .` 前**先看清范围**，**优先按路径精确 add**
- 改动前用 `git ls-files <path>` 确认文件是"已跟踪"还是"计划新增"，避免误判为删除
- 未跟踪文件丢失**不可恢复**，**建议高频提交**

### 7.2 行尾统一 LF

仓库根有 `.gitattributes`（`* text=auto eol=lf`）。
**编辑文件时不要整文件覆盖写回 CRLF**，否则会产生整文件 diff（历史上真的发生过）。

```bash
git ls-files --eol | grep w/crlf     # 检查：正常应为空
```

### 7.3 提交信息风格

格式为 `类型(范围): 中文描述`，参考现有历史：

```
feat(files): 上传图片自动转 WebP 以节省传输流量
fix(files): 文件不存在时不再下发 24 小时缓存头
docs: 同步 WebP、首个测试工程与 hero 压缩结果
refactor(auth)!: 合并两个登录页与两个登录端点为单一入口
```

类型：`feat`（新功能）/ `fix`（修 Bug）/ `docs`（文档）/ `refactor`（重构，不改变行为）/
`perf`（性能优化）/ `test`（测试）/ `chore`（杂项）。`!` 表示破坏性变更。

## 8. 部署

> **这一章的定位**：上线时照着从上往下做。**先本地跑通生产形态（§8.4），再买服务器** ——
> 这样远程部署时你只需要面对"服务器环境"这一个变量，而不是两个。

### 8.1 部署形态

**Linux + Nginx + 容器化**，Nginx 作为反向代理置于 Kestrel 之前：

```
浏览器 ──→ Nginx ──→ Kestrel(ASP.NET Core)
                └──→ 静态文件（前端构建产物）
```

四服务编排：`nginx`（唯一对外入口）/ `webapi` / `pgsql` / `redis`。

### 8.2 必须处理的四个点

| # | 问题 | 解法 |
|---|---|---|
| 1 | **SPA 的 history fallback**：前端用 `createWebHistory()`，直接刷新 `/post/xxx` 会 404（磁盘上没有这个文件） | Nginx 加 `try_files $uri $uri/ /index.html;` —— 已落地在 `deploy/nginx.conf` |
| 2 | **`X-Forwarded-For`**：加 Nginx 后 Kestrel 看到的来源 IP 全是 Nginx 的 IP，"按 IP 限流"退化成"全局限流" | ⚠️ **必须用 `$remote_addr` 覆盖，不能用 `$proxy_add_x_forwarded_for` 追加**——后者会保留客户端伪造值，而应用取的是第一段，**限流可被完全绕过**。详见 §8.6 |
| 3 | **工作目录**：`Logs` 与 `media` 是相对路径 | 容器里已用绝对路径 `FileStorage:Root=/app/media`（生产配置），并把 `/app/media`、`/app/logs` 挂成数据卷 |
| 4 | **上传体积**：Nginx 默认 `client_max_body_size` 只有 1 MiB，而上传接口允许 10 MiB | Nginx 设 `client_max_body_size 12m;`。不设的后果很隐蔽：**nginx 直接 413，后端日志里一片空白** |

> **开发期测不出第 1 点**：Vite dev server 内置了 fallback，"刷新 404"**只会在部署后暴露**。
> 第 1~4 点现在**都能在本地 compose 里复现**（见 §8.4），不必等到买服务器才发现。

### 8.3 生产必须做的配置

| 项 | 要求 |
|---|---|
| `Jwt:SigningKey` | 必须通过环境变量 `Jwt__SigningKey` 注入（**≥32 字节**）；`appsettings.*.json` 里**都没有**这一项，缺失时应用**拒绝启动** |
| **管理员密码** | ⚠️ **上线后第一件事**：改掉 `admin@example.com` 的密码。种子口令 `Admin@12345` **公开写在仓库里**（`BlogDbContext.cs` 的种子注释），而本仓库是 public —— 等于把后台钥匙挂在门上 |
| `ConnectionStrings__DefaultConnection` | 同样必须由环境变量注入（含密码），三个 appsettings 里都没有 |
| `POSTGRES_PASSWORD` | 不要沿用开发机的 `123456` |
| `Cache:Provider` | 生产用 `Redis`；`Deployment:InstanceCount > 1` 时 `DeploymentGuard` 会在启动期强制校验 |
| PostgreSQL | 必须使用带 zhparser 的镜像（`mixdeve/postgres-zhparser:18`），否则全文检索/还原都会失败 |
| `RateLimit` | 规则已落在 `appsettings.Production.json`；上线后按真实流量复查容量与速率 |
| `Cors:Origins` | 同源部署（Nginx 同时提供前端与 `/api`）时不需要 CORS，留空数组即可 |

改管理员密码有两条路：登录后台用「重置密码」接口，或直接改种子账号。
**不要**为了省事把密钥塞进 `appsettings.Production.json` —— 那个文件是入库的。

> ⚠️ **`appsettings.Production.json` 是 2026-09 新增的**，它修复了一个隐蔽缺陷：此前
> `Cache` / `FileStorage` / `RateLimit` 三节**只存在于开发配置**，生产环境会以
> 「限流开关开着、但规则列表为空」运行 —— **限流静默失效**。这类"开关是开的、
> 你以为它在工作"的配置缺陷，比直接报错危险得多。

### 8.4 本地整栈：先把生产形态跑起来

**这是推荐的部署路径**：用 `docker-compose.yml` 在本地跑起「生产形态」，确认无误后再搬到服务器。
编排产物：`docker-compose.yml`（四服务）、`deploy/{webapi,nginx}.Dockerfile`、`deploy/nginx.conf`、
`.env.example`（模板，真实 `.env` 已 gitignore）、`.dockerignore`（**必需**，见 §8.5 坑 A）。

```bash
# 在仓库根目录
cp .env.example .env                    # 填 JWT_SIGNING_KEY（openssl rand -base64 48）与 POSTGRES_PASSWORD
docker compose up -d --build            # 首次构建慢（拉 SDK/Node 镜像）
docker compose ps                       # 期望：nginx / webapi / pgsql / redis 四个都 healthy
curl -i http://localhost:8080/health    # 期望 200 + Healthy
docker compose logs -f webapi           # 看应用日志
docker compose down                     # 停止，数据保留在命名卷 / down -v 连卷一起删
```

实测（2026-09-14）`docker compose ps` 的输出中**每行都带 `(healthy)`**：
`blog-nginx-1`（`0.0.0.0:8080->80/tcp`）、`blog-pgsql-1`（`5432/tcp`）、
`blog-redis-1`（`6379/tcp`）、`blog-webapi-1`（`8080/tcp`）。

> ⚠️ **四个都要 healthy，nginx 不能漏。** 只发布 `nginx` 的 `8080` 端口；
> `pgsql` / `redis` **刻意不映射到宿主机**（① 避开开发用独立容器的 5432/6379；② 更接近生产）。
> 直连数据库用 `docker compose exec pgsql psql -U kky -d blog_stage2`。

**上线前还必须本地验这三件事**（接口连通性见 §5.3）：传一张 >1 MiB 的图**成功且后端日志有记录**
（被 nginx 拦掉时日志一片空白，§8.2 第 4 点）；伪造不同的 `X-Forwarded-For` 连发**仍被限流**（§8.6）；
`/assets/<hash>.js` 带 `Cache-Control: max-age=31536000, immutable`。

### 8.5 ⚠️ 容器化踩过的三个坑

| 坑 | 现象与根因 | 解法 |
|---|---|---|
| **A · 缺 `.dockerignore`** | `COPY Blog.Backend/ ./` 把宿主机上 **Windows 生成的 `obj/`**（`project.assets.json` 里记着 Windows 路径）复制进 Linux 容器，报 `MSB4018 ... Unable to find fallback package folder 'C:\Program Files (x86)\...'`。**迷惑点**：容器里的 `dotnet restore` 本来成功了，是随后的 `COPY` 覆盖掉了正确结果 | `.dockerignore` 排除 `**/bin`、`**/obj` |
| **B · Docker Hub 不可达** | `failed to resolve reference "docker.io/library/redis:<tag>"`。`mcr.microsoft.com` 通常可达，Docker Hub 不一定 | 给 Docker Desktop 配 registry mirror（Settings → Docker Engine 加 `"registry-mirrors": ["https://docker.m.daocloud.io"]`），配完重启 |
| **C · 健康检查写 `localhost`** | `HEALTHCHECK` 原写 `wget -qO- http://localhost/`，容器内报 `Connection refused`，而**宿主机 `curl localhost:8080/` 完全正常**。根因：Alpine 里 `localhost` 优先解析成 IPv6 `[::1]`，而 nginx 默认 `listen 80;` **只绑 IPv4** | ① `HEALTHCHECK` 地址写 `127.0.0.1`（`nginx.Dockerfile` / `webapi.Dockerfile`）；② `nginx.conf` 加 `listen [::]:80;` |

> **坑 C 的教训**：「服务能访问」和「探针说健康」是**两个独立的信号**。只验证前者，
> 你会带着一个永远 unhealthy 的容器上线 —— 而编排系统会因此拒绝启动下游服务
> （本项目 compose 正是用 `condition: service_healthy` 串起 `pgsql → webapi → nginx`）。
>
> 💡 三个坑的**完整推导过程**（含失败日志原文）在 `deploy/README.md` §6.4，这里只留结论。

### 8.6 ⚠️ 发现并修复的安全缺陷：限流可被绕过

**这是把栈真正跑起来才能发现的问题。**

| 测试 28 次请求 | 修复前 | 修复后 |
|---|---|---|
| A：正常请求 | 第 21 次起 `429` ✅ | 同左 ✅ |
| B：每次伪造不同的 `X-Forwarded-For` | **0 次 `429`**（完全绕过）❌ | **26 次 `429`** ✅ |

**根因是信任边界搞错了**：`nginx.conf` 原先用 `proxy_add_x_forwarded_for`
（nginx 文档里的常见范例），它把**客户端自己发的 `X-Forwarded-For` 保留在前面**再追加真实 IP；
而 `RateLimitingMiddleware.GetClientIp()` 取的是 `Split(',')[0]` ——
**第一段，也就是客户端完全可控的那一段**。于是每次换一个伪造 IP 就拿到一个全新的令牌桶。
**修复**：nginx 侧改用 `$remote_addr` **覆盖**整个头，把不可信输入丢掉：

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
```

> ⚠️ 该修复的前提是 **nginx 是唯一入口**（本项目 `webapi` 不对外发布端口）。
> 若前面再加 CDN / 云负载均衡，必须改用 `ngx_http_realip_module` 信任上游网段，
> **不能简单回到追加写法**。更彻底的做法是应用侧改用 `ForwardedHeadersMiddleware`
> + `KnownProxies`，即把「信任边界」表达在代码里而不是部署配置里 —— 见
> [06-技术债与待办.md](./06-技术债与待办.md)。

### 8.7 镜像交付与上线

上线把**镜像**搬过去，不是把源码搬过去现场构建：服务器上没有 .NET SDK / Node，
而 2 核 2G 上跑 `dotnet publish` + `vite build` 有 OOM 风险。

两条交付路径都由一个入口驱动：`tools/deploy/deploy.sh`。

| 路径 | 怎么做 | 传输量 | 什么时候用 |
|---|---|---|---|
| **GHCR 拉取（日常）** | 服务器 `bash tools/deploy/deploy.sh update <sha>` —— CI 会在合并进 main / 推 `v*` tag 后**自动执行**（见 §8.7.2） | 几 MB（Docker 按层拉） | 合并进 main 之后的每一次更新 |
| **本地打包（首装）** | 本地 `bash tools/deploy/deploy.sh build all` → `scp` → 服务器 `deploy.sh init <包> <域名>` | 约 350 MB（含 PG / Redis） | 首次部署，或服务器连不上 registry |

CI 的 `publish` 作业构建 `webapi` / `nginx` 并推 GHCR，tag 就是那次提交的 sha（见 §8.7.1）——
所以"线上跑的是哪个提交"有据可查；紧接着的 `deploy` 作业把服务器更新到同一个 sha。
**首次部署不在 CI 里**：那时服务器上还没有 compose 文件与 `.env`，必须人工走上面的本地打包路径。

服务器上需要的文件**只有这些**（源码不必上服务器）：`docker-compose.yml`、
`docker-compose.prod.yml`、`tools/deploy/deploy.sh`，外加首装时的镜像包 tar.gz。
**`.env` 不要从开发机传** —— `deploy.sh init` 会在服务器上现生成密钥；
开发机的密钥泄漏或复用，等于线上的 JWT 谁都能伪造。逐步命令见 `tools/deploy/README.md`。

**端口与防火墙**：只对外开 `80` / `443`。`deploy.sh init` 生成的 `.env` 里
`HTTP_PORT=127.0.0.1:8080`（只监听回环），由宿主机 Caddy 终结 TLS 再转发 ——
这一层由 `deploy.sh https <域名>` 装好（见 §8.8）。

#### 8.7.1 版本号与镜像 tag（发布流程）

**版本号的唯一来源是 git tag**：打一个 `v*` 形式的 tag 并推送，就是一次「发布」。

```bash
git tag -a v0.1.0 -m "首个基础版本"   # 语义化版本，必须带 v 前缀
git push origin v0.1.0               # 这一步才会触发流水线
```

> **约定：`v` + 语义化版本**（`v0.1.0`）。前缀不是装饰 —— CI 用 `refs/tags/v*` 判断
> 「这是一次发布」（`publish` / `deploy` 的 `if`，见 `.github/workflows/ci.yml`），
> 裸 `0.1.0` 只会推一个不触发任何作业的 tag，且不移动 `:latest`。
> 首次发布不必从 `v1.0.0` 起步：`0.x` 的惯例就是「接口还会变」。
> 这个 tag 同时是 **G4（发布流程）的实战验证** —— 在此之前流程只是"写好了"，见 [06-技术债与待办.md](./06-技术债与待办.md) §2。

CI（`.github/workflows/ci.yml`）对同一个镜像打**三个 tag**：

| tag | 例子 | 给谁用 | 会不会移动 |
|---|---|---|---|
| `:<完整 sha>` | `:0be5460a1b2c…` | **机器**：部署与回滚都认它 | ❌ 不可变 |
| `:<版本号>` | `:v0.1.0` | **人**：一眼看出是哪次发布 | ❌ 不可变 |
| `:latest` | `:latest` | "最新正式版"的便签 | ⚠️ **只在打版本 tag 时移动** |

前两个 tag 是**同一个镜像的别名**，不额外占存储。日常推 `main` 分支（未打 tag）时：

- 版本号取 `v0.0.0-main.<短sha>`，从名字就能看出「这不是一次正式发布」
- **不动 `:latest`** —— 这样它才等于「最新正式版」这个可靠含义

> ⚠️ **部署脚本永远用 `:<sha>`，不要用 `:latest`。** 它是会移动的标签，
> 出事时说不清线上跑的是哪一版（§8.9 的回滚流程用的是同一条理由）。

**确认线上版本**（部署完核对一次）：

```bash
curl -s https://<站点>/api/version
# {"code":0,"message":"ok","data":{"version":"v0.1.0","commit":"0be5460…","builtAt":"…"}}
```

端点说明见 [03-API参考.md](./03-API参考.md) §11.1。容器内也可直接看：
`docker compose exec webapi cat /app/version`。

**版本信息怎么进到镜像里**：CI 用 `--build-arg` 传 `VERSION` / `GIT_SHA` / `BUILD_TIME`，
`deploy/webapi.Dockerfile` 把它们写成 `ENV`（应用运行期读取），并落一份 `/app/version` 供人工排查。

> 💡 **为什么必须走 `--build-arg`，不能让 MSBuild 自己读 git**：
> 镜像的构建上下文只 `COPY Blog.Backend/`，**`.git` 根本不在镜像里**，
> MSBuild 的 `SourceRevisionId` 拿不到任何东西。
> 同理，本地构建的版本号（`Directory.Build.props` 里的 `0.0.0-local`）**不代表正式版本** ——
> 它只是让本地 `dotnet run` 时该端点有可读输出，避免显示成空白。

#### 8.7.2 自动部署（`deploy` 作业）

> **合并进 main 就是上线。** 这是当前唯一的日常上线方式 —— 没有"再点一下部署"这一步。

| 项 | 当前口径 |
|---|---|
| 触发 | `push` 到 `main`、或推 `v*` tag。**PR 与手动触发都不会部署**（手动触发的 ref 可以是任意分支，让它部署等于"把功能分支发到生产"） |
| 前置条件 | 一条链：`hygiene` / `frontend` / `backend` 三个检查作业**全部通过** → `publish` 推镜像成功 → `deploy`（`needs:` 串起来）。`security` 按设计只报告不阻断，不在门禁里 |
| 做什么 | ① 把仓库里的 `docker-compose.yml` / `docker-compose.prod.yml` / `tools/deploy/deploy.sh` 同步到服务器（顺带消掉"改了脚本但服务器那份没换"这种不报错的故障）；② SSH 到 `/opt/blog` 执行 `bash tools/deploy/deploy.sh update <完整 sha>` —— 脚本自己会 `pull` → 写 `.env` → `up -d` → `restart nginx` → 等 `/health` → 断言容器**真的**在跑新镜像；③ **从公网**核对 `GET /api/version` 里的 commit 就是这次的 sha |
| 并发 | 同一时间只允许一个部署（`concurrency: deploy-production`）。两次并发 `update` 会互相抢，先启动的那次若最后完成，线上就被退回旧 sha —— 而且它同样"成功" |
| 取消策略 | **main / tag 的运行不会被新推送取消**（只有 PR 会）。取消一个正在部署的运行会把线上留在半更新状态 |
| 代价 | 部署是**重建式**（`up -d` 换容器 + 重启 nginx），所以每次合并进 main 都会有几十秒的中断；**只改文档的合并也一样**——`publish` 不看改动内容，照样构建并推一个新 sha |
| 站点地址 | 第 ③ 步默认打 `https://www.kkynet.site`；换域名时加一个**仓库变量** `SITE_URL`（Settings → Secrets and variables → Actions → **Variables** 标签页）即可，不必改工作流 |

**需要的 GitHub 配置**（前三个缺一不可，且这类失败信息不具有指向性）：

| 类型 | 名称 | 说明 |
|---|---|---|
| Secret | `DEPLOY_HOST` | 服务器地址 |
| Secret | `DEPLOY_USER` | SSH 用户；需在 `docker` 组（`update` 不调 `sudo`） |
| Secret | `DEPLOY_SSH_KEY` | 私钥**全文**（含 `-----BEGIN/END-----` 两行）；对应公钥在服务器的 `~/.ssh/authorized_keys` |
| Secret（可选） | `DEPLOY_HOST_FINGERPRINT` | 服务器主机公钥的 SHA256 指纹。**填了就校验主机密钥（防中间人），不填则退回"不校验"**。取值：<br>`ssh <服务器> "ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub" \| cut -d ' ' -f2` |
| Variable（可选） | `SITE_URL` | 部署后核对版本的站点地址；不设则用 `https://www.kkynet.site` |

> ⚠️ **前三个必须是 Repository secrets**（Settings → Secrets and variables → Actions → **Secrets** 标签页）。
> 本仓库**没有配置任何 GitHub Environment**，所以建在 Environment 里的机密在作业里读不到；
> 建在隔壁 **Variables** 标签页的也不是 Secret（那是 `vars.*`，`secrets.*` 取不到值）。
> 两种情况的报错长得都像"连不上服务器"，而不是"变量没读到"。

> 💡 **服务器上的 `deploy.sh` 与两个 compose 文件现在由 CI 每次部署前同步**（`scp-action`，见上表第 ① 步），
> 所以不必再靠人记住"改了脚本要 scp"。两点要注意：
> - CI 同步会**覆盖**服务器上对这三个文件的本地修改 —— 想改配置请改仓库，让它同步下去；
> - **首次部署**与**绕过 CI 的手工部署**仍然要自己传，见 [tools/deploy/README.md](../tools/deploy/README.md) §2/§6。

**回滚**：`v*` tag 只影响镜像的 `:latest` 别名；线上永远跑 `:<sha>`。要退回去就把上一个 sha 的
部署再做一次（§8.9），或对旧提交推一个新 tag —— **不要**手工改 `.env` 了事。

### 8.8 HTTPS

**当前仓库里没有 HTTPS 配置**（`deploy/nginx.conf` 只有 `listen 80`）——
证书与域名是部署期才有的东西，不该进版本库。上线时二选一。

**"终结 TLS"是什么意思**：由某个进程持有证书、解密 HTTPS，再以**明文 HTTP** 转发给后面的容器。
它是加密的终点，容器栈内部仍然是明文。

```
浏览器 ──HTTPS──→ 宿主机 Caddy/Nginx ──HTTP(仅回环)──→ 容器 nginx ──→ webapi
                    ↑ 证书在这、TLS 在这终结
```

**为什么不在容器里做**：证书 90 天过期，续期必须自动化；而证书一旦进了镜像，
每次续期都要重新构建、重新传输（见 §8.7）。TLS 属于基础设施，不属于应用。

**方案一（推荐）：宿主机放一层 Caddy。** 选 Caddy 而不是 Nginx+certbot 的理由是
证书的**申请、续期、HTTP→HTTPS 跳转全自动**，配置只有三行（Nginx 方案要十几行加续期钩子）：

```
www.example.com {
	reverse_proxy 127.0.0.1:8080
}
example.com {
	redir https://www.example.com{uri} permanent
}
```

**方案二：把证书挂进 `nginx` 容器** —— 在 `deploy/nginx.conf` 加 `listen 443 ssl;` 的
server 块，compose 里把证书目录只读挂载并发布 `443`；续期后
`docker compose exec nginx nginx -s reload`。层数少一层，但续期要自己接钩子。

#### ⚠️ 8.8.1 加这一层**必须**同时启用 `realip`，否则限流会被打回原形

这是本项目实测确认过的连锁反应，也是本节最容易被跳过的一步。

| 步骤 | 发生了什么 |
|---|---|
| ① 容器 nginx 用 `$remote_addr` **覆盖** `X-Forwarded-For`（§8.6 的修复） | 这个写法在"nginx 是唯一入口"时是正确的 |
| ② 前面加了宿主机 TLS 层 | 容器 nginx 看到的对端**不再是访客**，而是 `127.0.0.1` / `172.x.0.1` |
| ③ 应用取 XFF **第一段**当限流 key（`RateLimitingMiddleware.GetClientIp`） | 所有访客被写成同一个 IP |
| ④ 结果 | 三条 `Granularity: Ip` 规则全部退化成**全站共享一个令牌桶**：`default` 120 次突发、`search` **20 次**。一个爬虫吃光搜索配额，所有正常访客一起 429 |

**修法是 4 行**（已落地在 `deploy/nginx.conf`）：

```nginx
set_real_ip_from 127.0.0.1;
set_real_ip_from 172.16.0.0/12;   # Docker 自定义网桥默认网段
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

**实测证据**（2026-09-14，用两个网段搭的最小复现：`inner 172.20.0.0/24` 模拟宿主机网段、
`outer 10.50.0.0/24` 模拟公网；真实访客 `10.50.0.2`，上游代理 `172.20.0.2`，
后端回显它收到的 `X-Forwarded-For`）：

| 场景 | 后端看到的客户端 IP | 结论 |
|---|---|---|
| ① 无 realip，经代理访问 | `172.20.0.2`（**上游代理的 IP**） | ❌ 全站归并成一个人 —— bug 复现 |
| ② 有 realip，经代理访问 | `10.50.0.2` | ✅ 真实访客 IP 恢复 |
| ③ 经代理 + 伪造 `XFF: 9.9.9.9` | `10.50.0.2` | ✅ 伪造无效 |
| ④ **绕过代理**直连容器 + 伪造 `XFF: 9.9.9.9` | `10.50.0.2` | ✅ 不可信对端的头被忽略 |

场景 ④ 的"绕过代理"一栏，正是下面那条安全论证的实证。

> ⚠️ **信任范围**：`172.16.0.0/12` 是整个 Docker 网桥网段，
> 意味着**同一网络里的其它容器**也能伪造这个头。本栈该网段上只有四个自家容器，
> 可以接受；将来若往这个网络里加不可信的第三方容器，要收紧成具体网段。

**为什么这样不会重新打开 §8.6 那个洞**：`realip` **只看对端地址**是否在信任列表里。

- 宿主机 Caddy 转发进来 → 对端 `127.0.0.1`（可信）→ 采信 XFF → 拿到真实访客 IP ✅
- 外部客户端直连 `8080` → 对端是公网 IP（不可信）→ **忽略**它伪造的 XFF，
  `$remote_addr` 仍是它自己的 IP ✅

也就是说，即使 `8080` 一时忘了关，限流也不会被绕过。

> ⚠️ **但仍然要把 `8080` 关掉、`HTTP_PORT` 绑回 `127.0.0.1`** ——
> 那是**绕过 TLS 的明文旁路**：走它登录，密码在公网上裸奔。
>
> ⚠️ 若将来前面再加 CDN，只需把 CDN 回源网段加进 `set_real_ip_from`，
> `real_ip_recursive on` 已经能处理多层链路。

**怎么验证真的生效了**（不验不算完）：

```bash
# 容器 nginx 的访问日志里应该还是**真实访客 IP**，不是 127.0.0.1
docker compose logs nginx | tail -20
```

### 8.9 回滚

> ⚠️ **本项目没有备份功能**（个人项目，不承担 RPO 承诺，见 [06 §4](./06-技术债与待办.md)）。
> 数据库那一半**没有任何自动兜底** —— 迁移出错只能写一个新迁移把结构改回来，或手工处理。

| 要回滚什么 | 怎么做 |
|---|---|
| **应用（代码/镜像）** | `bash tools/deploy/deploy.sh update <上一个 sha>`。镜像 tag 不可变，**回滚就是再部署一次旧 sha** |
| **配置** | `.env` / `docker-compose*.yml` 改回去，`scp` 到服务器后 `docker compose up -d` |
| **数据库（迁移出错）** | ⚠️ **回滚应用镜像不会回滚表结构。** 应用启动时自动跑 EF 迁移，而旧镜像不会把结构改回去；`dotnet ef` 也不支持自动回退已应用的迁移 |

> ⚠️ **镜像 tag 是可回滚性的前提**。别用 `latest` —— 那样"回滚"就成了
> "重新构建一次，希望拉到的还是旧代码"。用 git sha：CI 推的 tag 就是它。

> 📌 正因如此，**破坏性迁移（删列 / 改类型）要单独发布、并且想清楚再上**：
> 它是这套流程里唯一不可逆的操作。

### 8.10 部署拓扑校验（T5）

| `Deployment` 配置 | 结果 |
|---|---|
| `InstanceCount ≤ 1` 且 `RequireRedis = false` | 放行（允许内存实现） |

这是刻意的"启动期硬校验"——靠运行期静默降级极难排查。

## 9. 排错速查表

| 现象 | 最可能的原因 | 处理 |
|---|---|---|
| 前端全部 `ECONNREFUSED` | 后端进程已退出（**不是**被 bash 清理） | 查日志找退出原因，再用 `run_in_background=true` 重启（§2.5） |
| `curl` 被拒（WSL 内，连 5131/5173） | 那是 Windows 原生进程，WSL 到不了 | 用 Windows curl / Windows node（§2.1） |
| `curl` 被拒（WSL 内，连 8080） | 容器栈没起或没 healthy | `docker compose ps`（§8.4） |
| 命令报文件找不到，但工具明明装了 | 路径写成了 `/c/...` | 盘符是 `/mnt/c`（§1.1） |
| `ConnectionString ... not initialized` | 环境变量没传进 Windows 进程 | 加 `--environment Development`（§2.2） |
| `Cannot find native binding` | 用了 WSL 的 node | 用 Windows node（§2.3） |
| `MSB3027` / `MSB3021` | 运行中的 exe 锁了 DLL；csproj 的自动 Target 实测拦不住 | `taskkill /F /IM Blog.WebApi.exe`（§2.3） |
| `dotnet` 报 `path1` 空引用 | 当前会话缺 Windows 环境变量 | 用 §2.6 的内联 `env ...` 形式 |
| `text search configuration "chinese" does not exist` | 连到了不带 zhparser 的 PG | 换 `mixdeve/postgres-zhparser:18`（§2.6） |
| 容器一直 `unhealthy` 但外部访问正常 | 健康检查写了 `localhost`（解析到 IPv6） | 改 `127.0.0.1` + `listen [::]:80`（§8.5 坑 C） |
| 上传大图后后端日志**一片空白** | nginx 413（默认 1 MiB 上限） | `client_max_body_size 12m;`（§8.2 第 4 点） |
| 限流形同虚设 | nginx 用了 `$proxy_add_x_forwarded_for` | 改 `$remote_addr` 覆盖（§8.6） |
| 刷新 `/post/xxx` 404（本地开发却正常） | SPA history fallback 没配 | `try_files $uri $uri/ /index.html;`（§8.2 第 1 点） |
| 接口 500 且无业务日志 | 未处理异常 | 查日志 ERR 级 + 完整堆栈（§3.2） |
| 返回 401 但前端没跳登录 | 该请求不是经 `http.ts` 发出的 | 检查是否绕过封装 |
| 400/404 却记成 ERR 500 | 请求日志中间件注册顺序错了 | 见 [02-架构与数据模型.md](./02-架构与数据模型.md) |
| 保存文章必 500，日志有 `23505 ... PK_PostCollections` | 改多对多连接集合时没 Include 导航 | 用 `GetWithPostsAsync`（见 [02-架构与数据模型.md](./02-架构与数据模型.md) §7） |
| 保存文章必 500，日志有 `23505 ... PK_PostTag` | 标签整体替换而非增量同步 | 用增量同步（见 [02-架构与数据模型.md](./02-架构与数据模型.md) §7） |
| 列表"共 N 篇"显示 `undefined` | 后端字段是 `total`，前端写成 `totalCount` | 对齐为 `total` |
| 后台点一次编辑，浏览量 +1 | 编辑器用了计数的详情接口 | 改用 `/readonly` |
| 搜索结果相关度不对 | 检查 `zhparser`/`chinese` 配置是否可用 | `GET /health` 会直接验一次分词（见 [03-API参考.md](./03-API参考.md)） |
| 浏览器一直显示空白背景 | 曾经的 404 被缓存了一整天 | 强刷；若复现见 [02-架构与数据模型.md](./02-架构与数据模型.md) |
| `git status` 一片红但内容没变 | 行尾被写成了 CRLF | 见 §7.2 |
| **改了数据，但接口 / 页面还是旧的** | ⚠️ **应用层缓存**（专栏 / 分类 / 标签 / 文章列表都有缓存） | 先确认是不是**绕过程序直接改的库**（`psql` / SQL）—— 那样应用的失效逻辑不可能知道。清掉相应键：<br>`docker exec -i redis redis-cli --scan --pattern 'blog:taxonomy:*' \| xargs -r docker exec -i redis redis-cli DEL`<br>键名规则见 `Blog.Application/Interfaces/CacheKeys.cs`；过程见 [archive/问题排查记录.md](../archive/问题排查记录.md) 第 11 条 |
| 后端进程"自己没了"，日志无异常、**退出码 0** | **被外部终止**（人工停掉 / 后台作业被回收 / 构建时的 `KillRunningBlogWebApi`）—— **不是崩溃** | 崩溃会留 `FTL` + 堆栈；没有就等于外部信号。重启并用文件记录日志（§2.4） |
