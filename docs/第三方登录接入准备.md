# 第三方登录接入准备（GitHub / 飞书）

> 状态：等待管理员提供平台凭据与回调地址
> 对应步骤：三步实现中的第 1 步（平台调研 + 凭据准备）
> 最后更新：2026-11-05
> 适用方案：绑定方案 A —— 只允许已有 Admin 账号绑定第三方身份，不开放注册

---

## 0. 一分钟版

你需要做 5 件事：

1. 用**个人 GitHub 账号**创建一个 OAuth App，回调填 `http://localhost:5173/api/auth/external/github/callback`（生产再加 HTTPS 地址），不申请 scope。
2. 用飞书企业/团队创建一个**企业自建应用**（需要开发者/管理员权限；非管理员需找企业管理员），添加「网页应用」能力，在「安全设置 → 重定向 URL」填 `http://localhost:5173/api/auth/external/feishu/callback`（生产再加 HTTPS 地址），**不申请通讯录权限**。
3. 飞书应用选择测试版（免审）或提交正式版审核；确保你的飞书账号在「可用范围」内。
4. 把 App ID / Client ID / 回调地址 / 生产域名填进 `ExternalAuth` 配置；两个 Secret 只放环境变量或 `.env`。
5. 告诉我「配置已填好」，附上非敏感值；**不要发 Secret**。

> 下面的示例默认用 Vite 开发服务器 `http://localhost:5173`。如果你像当前配置一样走 Docker Compose 的 Nginx（`http://localhost:8080`），把所有 `5173` 换成 `8080`，并确保两个平台后台的回调地址也同步改成 `8080`。

详细步骤、自测命令和常见错误见下文。

## 1. 范围与已确认事项

### 1.1 本次要做的事

- 保留现有邮箱 + 密码登录。
- 新增 GitHub 网页跳转授权登录。
- 新增飞书网页跳转授权登录。
- 新增飞书扫码登录（PC 登录页展示二维码，飞书移动端扫码确认）。
- 管理员登录后，在后台配置页把「当前账号」与 GitHub / 飞书账号绑定。
- 绑定后，管理员可以用密码、GitHub 或飞书任一方式登录。

### 1.2 本次不做的事

- 不开放自助注册。
- 不自动创建账号。
- 不按第三方邮箱自动关联账号。
- 不存储第三方昵称、头像、邮箱、手机号等资料。
- 不存储第三方 `access_token` / `refresh_token`。
- 不调用 GitHub / 飞书的业务 API（只做登录证明）。
- 不做读者账号体系（评论仍由 giscus 承担）。

### 1.3 只存「登录证明」

绑定表最终只保留以下字段（具体表名在实现阶段确定）：

| 字段 | 示例 | 说明 |
|---|---|---|
| `UserId` | 本站用户 Id | 关联当前管理员账号 |
| `Provider` | `GitHub` / `Feishu` | 第三方平台 |
| `ProviderUserId` | GitHub `12345678` / 飞书 `ou_xxx` | 平台侧稳定用户标识 |
| `CreatedAt` / `LastLoginAt` | 时间 | 绑定与最近登录审计 |

**不存**：姓名、昵称、头像、邮箱、手机号、`tenant_key`、第三方 token、第三方原始响应。

> `tenant_key` 不落库；它只作为 `ExternalAuth:Feishu:TenantKey` 配置，在登录时与第三方返回值比对。绑定表里只有 `Provider + ProviderUserId + UserId + 时间`。

> 后台绑定页只显示「已绑定 GitHub / 已绑定飞书」，不显示第三方账号名或头像；绑定状态接口也只返回 provider + 是否绑定。若以后想显示「已绑定 @xxx」，就必须额外存第三方用户名——这与当前「不存额外资料」的要求冲突，需要单独确认。

### 1.4 绑定页与登录页的行为

- 绑定入口：管理员用密码登录后，在后台配置页操作；未登录不能绑定。
- 绑定对象：当前登录的 Admin 账号；一个账号可以同时绑定 GitHub 和飞书。
- 同一个第三方身份如果已经绑定到另一个本站账号，拒绝再次绑定并提示联系管理员；不自动转移。
- 解绑：允许，解绑后仍可用密码登录；如果解绑后没有任何登录方式，则不允许（当前密码始终存在，所以暂不触发）。
- 第三方登录时：
  - 查到绑定 → 为对应本站账号签发会话。
  - 查不到绑定 → 回到登录页提示「该账号尚未绑定，请先用密码登录后在后台绑定」，**不自动注册**。
  - 绑定账号被停用 → 按现有账号停用逻辑拒绝，不泄露具体原因。
- 当前按「仅 Admin 角色可绑定」理解；如果 Author 也要绑定，请告知，会影响路由和接口策略，但不影响平台配置。

## 3. 两个平台的差异速览

| 维度 | GitHub | 飞书 |
|---|---|---|
| 应用类型 | OAuth App（个人账号即可） | 企业自建应用（需要飞书企业/团队） |
| 授权协议 | OAuth 2.0 authorization code | OAuth 2.0 authorization code |
| 用户身份来源 | `GET /user` 的 `id` | `GET /authen/v1/user_info` 的 `open_id` |
| 最小权限 | 可不申请 scope，只读公开资料 | 基础字段不需要 scope |
| 是否支持 PKCE | 支持（S256） | 新版 v3 暂不支持；旧流程也不支持 |
| 第三方 token 寿命 | 默认 8 小时（可配置），有 refresh_token | user token 约 2 小时；refresh token 约 7–30 天 |
| 网页跳转登录 | 支持 | 支持（新版 v3） |
| 扫码登录 | 无原生扫码 | 官方二维码 SDK（旧授权链路） |
| 租户限制 | 无 | `tenant_key`；自建应用只服务本租户 |
| 发布审核 | 无，创建即用 | 测试版免审；正式版需要企业管理员审核 |
| 用户资料默认返回 | 公开资料（我们只用 `id`） | 姓名/头像/open_id/tenant_key（我们只用 `open_id`） |

两边的**后端形状是一样的**：拼授权 URL → callback 拿 `code` → 换 token → 调用户信息 → 取稳定 ID → 查绑定。差异全部收敛在 provider 适配层。

## 4. GitHub 接入

### 4.1 平台选择与政策限制

**选择 OAuth App，不选 GitHub App。**

- 本次只做登录，不需要仓库权限、不需要安装到组织、不需要长期 API 调用。
- GitHub App 更适合细粒度仓库权限和短期 token；对本项目是过度设计。
- OAuth App 创建即用，没有审核等待。

**关键限制：**

1. **回调地址必须精确匹配。**
   - OAuth App 最多可配置 10 个 callback URL。
   - 生产必须 HTTPS；开发可用 `http://localhost:5173/...`。
   - 不要开启 wildcard matching（老应用可能默认开启，建议在设置里关闭）。
   - 回调地址不要带 query / fragment，不要漏掉 `/api/...` 路径。
2. **最小权限。**
   - GitHub 的 `(no scope)` 已允许读取公开资料，包括用户 profile；本次只读数字 `id`，计划**不申请任何 scope**。
   - 如果实测 `GET /user` 因权限失败，才加 `read:user`；**绝不申请** `user:email`、`repo`、`read:org`。
   - 不请求邮箱，避免「按邮箱自动关联」的诱惑。
3. **Token 不落地。**
   - OAuth App 的 “Expire user access tokens” 默认开启；access token 约 8 小时有效，可能同时返回 `refresh_token`。
   - 我们只用 access token 调一次 `GET /user`，随后丢弃，并调用 GitHub 的撤销接口把该 token 撤销；不存 refresh token。
   - 不使用 Device Flow。
4. **用户可随时撤销授权。**
   - 用户在 GitHub `Settings → Applications` 里撤销后，下一次登录会在授权页被拒绝或拿不到新 token；此时按「未绑定/授权失败」处理，不自动恢复。
5. **组织策略。**
   - 如果 OAuth App 归组织所有，或你的 GitHub 账号属于启用了 OAuth App 限制 / SAML SSO 的组织，授权可能被组织管理员拦截。
   - 个人博客建议用**个人账号**创建 OAuth App，避免组织审批。
6. **公开信息。**
   - OAuth App 的 name、homepage、description 对授权用户可见，不要填内部地址、测试密码等敏感内容。
   - 登录按钮使用 GitHub 官方标识，不暗示 GitHub 官方背书。
7. **品牌与合规。**
   - 仅用于本站登录，不抓取用户数据、不发送推广信息。
   - 如果站点面向公众，建议在隐私说明中写明「使用 GitHub 登录时仅读取公开用户标识」。

### 4.2 创建步骤

1. 登录你的 GitHub **个人账号**。
2. 右上角头像 → **Settings** → 左侧 **Developer settings** → **OAuth Apps** → **New OAuth App**。
3. 填写：
   - **Application name**：例如 `Kky Blog Admin`（公开可见，不要写敏感词）。
   - **Homepage URL**：开发期可填 `http://localhost:5173`；生产填 `https://<你的域名>`。
   - **Application description**：可选，例如 `Personal blog admin sign-in`。
   - **Authorization callback URL**：
     - 开发：`http://localhost:5173/api/auth/external/github/callback`
     - 生产：`https://<你的域名>/api/auth/external/github/callback`
     - 可以点 **Add callback URL** 把两个都加上；后续在配置里按环境选一个。
4. **Enable Device Flow**：保持关闭。
5. **Expire user access tokens**：保持默认开启即可；我们不会保存 token。
6. 点击 **Register application**。
7. 在应用页复制 **Client ID**。
8. 点击 **Generate a new client secret**，复制 **Client Secret**（只显示一次；丢失就重新生成）。
9. 如果页面出现 callback URL 的 wildcard matching 选项，关闭它；删除不再使用的旧回调。

> 开发期建议统一使用 `localhost`，不要一会儿 `localhost`、一会儿 `127.0.0.1`。浏览器 Cookie 按 host 隔离，混用会导致登录态对不上。

### 4.3 需要填入的配置

```json
"ExternalAuth": {
  "GitHub": {
    "Enabled": true,
    "ClientId": "Iv1.xxxxxxxxxxxx",
    "ClientSecret": "",
    "RedirectUri": "http://localhost:5173/api/auth/external/github/callback",
    "Scopes": ""
  }
}
```

- `ClientSecret` 留空在文件里，通过环境变量注入（见第 6 节）。
- `Scopes` 留空表示不申请 scope；如果实测需要，填 `read:user`，不要加别的。
- `RedirectUri` 必须与 GitHub 后台逐字符一致（协议、host、端口、路径）。

### 4.4 实现前如何自测

1. 在浏览器打开（把 `CLIENT_ID` 和 `REDIRECT_URI` 换成你的值）：

```
https://github.com/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&state=test-state
```

2. 点授权。浏览器应跳回：

```
http://localhost:5173/api/auth/external/github/callback?code=...&state=test-state
```

   此时后端接口还没实现，页面可能 404 或返回统一 JSON，这是正常的；关键是 URL 里有 `code` 和 `state`。

3. 复制 `code`，用 curl 换 token（**在本地终端执行，不要把 secret 贴到聊天**）：

```bash
curl -sS -X POST https://github.com/login/oauth/access_token \
  -H "Accept: application/json" \
  -d "client_id=CLIENT_ID" \
  -d "client_secret=CLIENT_SECRET" \
  -d "code=CODE" \
  -d "redirect_uri=REDIRECT_URI"
```

4. 用返回的 `access_token` 调：

```bash
curl -sS https://api.github.com/user \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "User-Agent: blog-admin-login-check"
```

   确认返回里有 `"id": 12345678`；这个数字就是以后唯一要存的 GitHub 标识。`login` 可能改名，不要用它做键。

5. 验证完撤销 token：

```bash
curl -sS -X DELETE "https://api.github.com/applications/CLIENT_ID/token" \
  -u "CLIENT_ID:CLIENT_SECRET" \
  -H "Accept: application/vnd.github+json" \
  -d '{"access_token":"ACCESS_TOKEN"}'
```

   返回 204 即撤销成功。

### 4.5 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `redirect_uri` mismatch | 后台配置与请求值不完全一致 | 逐字符核对协议、host、端口、路径、末尾 `/` |
| 回调 404 | 后端路由还没实现，或 Vite 代理没开 | 自测阶段只看 URL 是否有 code；实现后再验 |
| 授权页没有请求的权限 | `scope` 为空 | 这是预期；我们只要公开 `id` |
| `GET /user` 返回 401/403 | token 无效或 scope 不足 | 重新走授权；必要时只加 `read:user` |
| 组织 SSO 拦截 | 账号属于受限制组织 | 用个人账号创建 OAuth App，或联系组织管理员 |
| secret 泄露 | 曾提交到 Git / 日志 | 立即在 GitHub 重新生成 secret，更新环境变量 |

## 5. 飞书接入

### 5.1 平台选择与政策限制

**选择企业自建应用（Custom App），不选商店应用。**

- 本站是内部管理员登录，不需要上架应用商店，也不需要 ISV 多租户。
- 自建应用只服务你自己的飞书企业/团队，天然限制登录人群。
- 需要飞书企业/团队，以及开发者或管理员权限；如果只是普通成员，需要企业管理员协助创建/发布应用。

**关键限制：**

1. **应用可用范围。**
   - 自建应用发布时要设置「可用范围」；只有范围内的成员才能授权。
   - 如果范围不含你的账号，授权会报 `20010`（用户无应用使用权限）。
   - 建议正式环境先只把管理员本人加入范围，验证后再按需扩大。
2. **测试版 vs 正式版。**
   - 开发阶段推荐使用「测试企业和人员」：测试版应用配置变更直接生效，不需要企业管理员审核。
   - 正式上线需要「应用发布 → 版本管理与发布 → 创建版本 → 申请线上发布」，由企业管理员审核通过后生效。
   - **这是飞书侧最大的等待项**，建议先创建应用并提交发布，避免实现完成后卡在审核。
   - 测试企业与正式企业的用户是两套；测试账号的 `open_id` 不保证与正式账号相同，测试期绑定只用于联调，正式上线后请用正式账号重新绑定。
3. **回调地址必须精确匹配。**
   - 在「开发配置 → 安全设置 → 重定向 URL」中添加。
   - 支持配置多个；协议、host、端口、路径必须与请求中的 `redirect_uri` 完全一致。
   - 生产必须 HTTPS；本地测试可用 `http://localhost:5173/...` 或 `http://127.0.0.1:5173/...`（测试企业）。
   - 不要带 query / fragment。
4. **权限：本次不需要申请任何通讯录权限。**
   - `GET /authen/v1/user_info` 的 `name`、`avatar_url`、`open_id`、`union_id`、`tenant_key` 等基础字段**不需要 scope**。
   - `user_id`、邮箱、手机号、员工信息才需要额外权限；我们**不申请、不读取、不存储**。
   - 如果控制台/接口强制要求，才最小化申请 `contact:user.base:readonly`；绝不申请 `contact:user.email:readonly`、`contact:user.phone:readonly`、`contact:user.employee_id:readonly`。
5. **扫码 SDK 是官方提供的第三方脚本。**
   - 脚本地址：`https://lf-package-cn.feishucdn.com/obj/feishu-static/lark/passport/qrcode/LarkSSOSDKWebQRCode-1.0.3.js`
   - 它使用旧的 `passport.feishu.cn` 授权页，官方文档明确写「暂不支持新版登录流程」。
   - 扫码确认后，页面通过 `postMessage` 收到 `tmp_code`，再跳转到授权页拼接 `tmp_code`；飞书最终 302 回你的回调地址，带普通 `code` 和 `state`。
   - 授权码 5 分钟有效、只能使用一次。
   - 该流程不支持 scope，也不支持 PKCE；靠 `state` + 后端 client secret + 一次性 code 保证安全。
   - 生产页面必须 HTTPS；本地 `localhost` / `127.0.0.1` 可调试。
6. **网页跳转登录用新版 v3。**
   - 授权页：`https://accounts.feishu.cn/open-apis/authen/v1/authorize`
   - Token：`https://accounts.feishu.cn/oauth/v3/token`
   - 用户信息：`https://open.feishu.cn/open-apis/authen/v1/user_info`
   - 当前飞书文档说明：新版授权页的 PKCE 暂时只能配 v2 token 端点，v3 还不支持；所以飞书这条链路**不使用 PKCE**，用 `state` + 精确回调 + 后端 secret。
7. **`open_id` 是应用内唯一标识。**
   - 同一个飞书用户，在同一个应用内 `open_id` 稳定；不同应用不同。
   - **不要删除重建飞书应用**：重建后 `open_id` 会变，已有绑定全部失效，需要重新绑定。
   - 如果担心重建应用，可额外存 `union_id` 作为兜底（仍是登录标识，不是资料）；当前默认只存 `open_id`，是否加存需你确认。
8. **租户限制。**
   - 自建应用本身只服务本企业；`user_info` 会返回 `tenant_key`。
   - 可以在配置里填 `TenantKey`，登录时比对；不匹配直接拒绝。留空则不额外校验。
   - 企业编号可在飞书管理后台「企业设置 → 企业信息 → 企业信息管理」查看，或从首次测试登录的 `tenant_key` 获取。
9. **不需要配置事件订阅。**
   - 本次只做登录，不接收飞书事件，不需要 Encrypt Key / Verification Token。
10. **IP 白名单。**
    - 如果企业开启了应用 IP 白名单，需要把后端服务器的出口公网 IP 加入，否则 token 交换会被拒。
11. **品牌与隐私。**
    - 登录按钮使用飞书官方标识；应用名称/图标不要冒充官方。
    - 仅读取登录标识，不读取通讯录、不存资料。
    - App Secret 只放后端；如怀疑泄露，在「凭证与基础信息」重置并同步更新环境变量。

### 5.3 飞书扫码登录的官方链路（按你给的教程）

前端：

1. 在登录页引入官方 SDK：

```html
<script src="https://lf-package-cn.feishucdn.com/obj/feishu-static/lark/passport/qrcode/LarkSSOSDKWebQRCode-1.0.3.js"></script>
```

2. 构造 `goto`（必须是旧版 `passport.feishu.cn` 授权页，SDK 不支持新版）：

```
https://passport.feishu.cn/suite/passport/oauth/authorize
  ?client_id=<App ID>
  &redirect_uri=<URL 编码后的回调地址>
  &response_type=code
  &state=<随机 state>
```

3. 调用 `window.QRLogin({ id, goto, ... })` 渲染二维码。
4. 监听 `message`，用 SDK 的 `matchOrigin` / `matchData` 校验来源和数据；收到 `tmp_code` 后跳转：

```
`${goto}&tmp_code=${tmp_code}`
```

5. 飞书会 302 到回调地址，带 `code` 和 `state`。

后端：

1. 用 App ID / App Secret 换应用凭证：

```
POST https://open.feishu.cn/open-apis/auth/v3/app_access_token/internal
Content-Type: application/json

{ "app_id": "...", "app_secret": "..." }
```

   响应里同时有 `app_access_token` 和 `tenant_access_token`。官方 demo 取的是 `tenant_access_token`，而接口文档写的是 `app_access_token`；实现时先用官方 demo 的取值跑通，再按接口文档核对。两者都只来自 App ID / App Secret，不涉及用户数据。

2. 用应用凭证 + `code` 换用户 token：

```
POST https://open.feishu.cn/open-apis/authen/v1/oidc/access_token
Authorization: Bearer <app_access_token>
Content-Type: application/json

{ "grant_type": "authorization_code", "code": "<code>" }
```

   取 `data.access_token`（user_access_token）。这是官方扫码教程当前使用的历史端点；实现时先按教程跑通，再评估是否可切 v3。

3. 用 user token 取用户信息：

```
GET https://open.feishu.cn/open-apis/authen/v1/user_info
Authorization: Bearer <user_access_token>
```

   只取 `data.open_id`（以及可选的 `tenant_key` 做校验），**不读取、不存储** `name` / `avatar_url` / `email` / `mobile` / `user_id`。

4. 立即丢弃 user token，不存 refresh token。

**安全说明：** 这条链路没有 PKCE。防 CSRF 靠 `state`（后端生成、加密 cookie 保存、回调比对），防 code 重放靠飞书 5 分钟一次性 code，防伪造靠 client secret 只在后端。二维码 SDK 的 `matchOrigin` / `matchData` 必须校验，不能直接信任 `message`。

### 5.4 飞书网页跳转登录的新版链路

1. 授权页：

```
https://accounts.feishu.cn/open-apis/authen/v1/authorize
  ?client_id=<App ID>
  &redirect_uri=<URL 编码后的回调地址>
  &response_type=code
  &state=<随机 state>
```

   本次不传 `scope`，不申请权限。

2. 回调拿到 `code` 后换 token：

```
POST https://accounts.feishu.cn/oauth/v3/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&client_id=<App ID>
&client_secret=<App Secret>
&code=<code>
&redirect_uri=<回调地址>
```

3. 用返回的 `access_token` 调 `user_info`，只取 `open_id` / `tenant_key`。

**注意：** 飞书当前文档说明新版授权页的 PKCE 只能配 v2 token 端点，v3 暂不支持；因此这条链路不用 PKCE。GitHub 那条链路仍然用 PKCE S256。

### 5.5 需要填入的配置

```json
"ExternalAuth": {
  "Feishu": {
    "Enabled": true,
    "AppId": "cli_xxxxxxxxxxxx",
    "AppSecret": "",
    "RedirectUri": "http://localhost:5173/api/auth/external/feishu/callback",
    "TenantKey": "",
    "Scopes": "",
    "EnableQr": true
  }
}
```

- `AppSecret` 留空在文件里，通过环境变量注入（见第 6 节）。
- `Scopes` 留空；不要为了「多拿点信息」加权限。
- `TenantKey` 可留空；建议测试成功后填上，限制只允许本企业。
- `EnableQr` 控制登录页是否显示扫码入口；如果飞书应用还没发布，可以先设为 `false`。

### 5.6 实现前如何自测

**网页跳转 / v3 链路：**

1. 浏览器打开（替换 `APP_ID` / `REDIRECT_URI`）：

```
https://accounts.feishu.cn/open-apis/authen/v1/authorize?client_id=APP_ID&redirect_uri=REDIRECT_URI&response_type=code&state=test-state
```

2. 用可用范围内的飞书账号授权，浏览器应回到：

```
http://localhost:5173/api/auth/external/feishu/callback?code=...&state=test-state
```

3. 复制 `code`，换 token：

```bash
curl -sS -X POST https://accounts.feishu.cn/oauth/v3/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=authorization_code" \
  -d "client_id=APP_ID" \
  -d "client_secret=APP_SECRET" \
  -d "code=CODE" \
  -d "redirect_uri=REDIRECT_URI"
```

4. 用 `access_token` 调：

```bash
curl -sS https://open.feishu.cn/open-apis/authen/v1/user_info \
  -H "Authorization: Bearer USER_ACCESS_TOKEN"
```

   确认返回 `code: 0`，且 `data.open_id` 存在；`tenant_key` 可用来填配置。

**扫码链路：**

- 官方扫码教程的前端 demo 使用 `http://127.0.0.1:3001/qrLogin`，并需要在该应用的「重定向 URL」里临时加入这个地址。
- 你也可以等我们实现登录页后，用真实页面扫码验证；在配置准备阶段，先确保：
  - 应用是测试版或已发布；
  - 你的飞书账号在可用范围内；
  - 回调地址已加入；
  - 网页应用能力已添加。
- 扫码验证时，用飞书移动端扫 PC 页面二维码，确认后应回到回调地址并带 `code` / `state`；后端应能换到 `open_id`。

### 5.7 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 授权报 `20010` | 用户不在应用可用范围 | 把账号加入可用范围；或先用测试企业 |
| `redirect_uri` 不匹配 | 安全设置里没有这个完整地址 | 逐字符核对协议、host、端口、路径 |
| 应用未发布/配置不生效 | 正式版需要版本审核 | 用测试版先联调；正式版提交发布并等管理员审核 |
| 扫码后没有 `tmp_code` | SDK 未加载、页面非 HTTPS/localhost、`message` 校验失败 | 检查脚本、`matchOrigin`/`matchData`、监听逻辑 |
| 扫码 SDK 不认新授权页 | 官方 SDK 只支持旧 `passport.feishu.cn` 流程 | `goto` 用旧地址；不要换成新 `accounts.feishu.cn` |
| code 过期 | 授权码 5 分钟有效 | 重新扫码/重新授权 |
| `20027` | 请求了未开通的 scope | 本次不申请 scope；如确需，先在权限管理开通 |
| `open_id` 变了 | 删除重建了飞书应用 | 不要重建；已绑定用户需要重新绑定 |
| token 交换 403 | 企业 IP 白名单 / 应用未启用 | 加服务器出口 IP；检查应用状态 |
| H5 可信域名报错 | 只影响 JSAPI 免登，不影响扫码 SDK | 本次可忽略；如用客户端内免登再配 |

## 6. 配置模板与密钥注入

### 6.1 配置文件位置

- 开发：`Blog.Backend/Blog.WebApi/appsettings.Development.json`
- 生产：`Blog.Backend/Blog.WebApi/appsettings.Production.json`
- 非敏感值（App ID、Client ID、回调地址、TenantKey）可以写进上述文件。
- **敏感值（Client Secret / App Secret）不要写进任何 `appsettings` 文件，也不要提交 Git。**
- 这些 `ExternalAuth` 键在实现阶段才会被读取；现在填入不会改变现有登录行为，也不会让登录页自动出现第三方按钮。

### 6.2 完整模板

```json
"ExternalAuth": {
  "FrontendBaseUrl": "http://localhost:5173",
  "GitHub": {
    "Enabled": true,
    "ClientId": "Iv1.xxxxxxxxxxxx",
    "ClientSecret": "",
    "RedirectUri": "http://localhost:5173/api/auth/external/github/callback",
    "Scopes": ""
  },
  "Feishu": {
    "Enabled": true,
    "AppId": "cli_xxxxxxxxxxxx",
    "AppSecret": "",
    "RedirectUri": "http://localhost:5173/api/auth/external/feishu/callback",
    "TenantKey": "",
    "Scopes": "",
    "EnableQr": true
  }
}
```

生产环境把 `FrontendBaseUrl`、两个 `RedirectUri` 换成 `https://<你的域名>`。

`FrontendBaseUrl` 是回调成功后跳回前端的地址。如果前后端同源（例如 Nginx 同时提供前端和 `/api`，你在 `http://localhost:8080` 访问），它可以留空，后端用相对路径跳转；如果前后端不同源，必须填完整地址。

### 6.3 密钥注入

**方式 A：本地环境变量（推荐，先跑通）**

Linux / WSL / macOS：

```bash
export ExternalAuth__GitHub__ClientSecret='github-client-secret'
export ExternalAuth__Feishu__AppSecret='feishu-app-secret'
dotnet run --project Blog.Backend/Blog.WebApi
```

PowerShell：

```powershell
$env:ExternalAuth__GitHub__ClientSecret = 'github-client-secret'
$env:ExternalAuth__Feishu__AppSecret = 'feishu-app-secret'
dotnet run --project Blog.Backend/Blog.WebApi
```

> .NET 的分层配置用双下划线：`ExternalAuth__GitHub__ClientSecret` 对应 `ExternalAuth:GitHub:ClientSecret`。

**方式 B：Docker Compose `.env`**

在根目录 `.env` 中加：

```dotenv
GITHUB_CLIENT_SECRET=
FEISHU_APP_SECRET=
```

实现阶段会在 `docker-compose.yml` 的 `webapi.environment` 中映射为：

```yaml
ExternalAuth__GitHub__ClientSecret: ${GITHUB_CLIENT_SECRET:?GITHUB_CLIENT_SECRET 未设置}
ExternalAuth__Feishu__AppSecret: ${FEISHU_APP_SECRET:?FEISHU_APP_SECRET 未设置}
```

`.env` 已被 Git 忽略；`.env.example` 只放空值模板，不填真实 secret。

**方式 C：user-secrets**

实现阶段给 `Blog.WebApi` 加 `UserSecretsId` 后可用：

```bash
dotnet user-secrets set "ExternalAuth:GitHub:ClientSecret" "..." --project Blog.Backend/Blog.WebApi
dotnet user-secrets set "ExternalAuth:Feishu:AppSecret" "..." --project Blog.Backend/Blog.WebApi
```

在加 `UserSecretsId` 之前，优先用环境变量。

### 6.4 开发/生产回调地址对照

| 环境 | `FrontendBaseUrl` | GitHub `RedirectUri` | 飞书 `RedirectUri` |
|---|---|---|---|
| Vite 开发 | `http://localhost:5173` | `http://localhost:5173/api/auth/external/github/callback` | `http://localhost:5173/api/auth/external/feishu/callback` |
| Docker / Nginx 同源 | 可留空或 `http://localhost:8080` | `http://localhost:8080/api/auth/external/github/callback` | `http://localhost:8080/api/auth/external/feishu/callback` |
| 生产 | `https://<域名>` | `https://<域名>/api/auth/external/github/callback` | `https://<域名>/api/auth/external/feishu/callback` |

注意：

- 开发期 Vite 把 `/api` 代理到 `http://localhost:5131`，所以回调走 `5173` 也能到后端。
- 如果改用 `127.0.0.1`，全链路都改成 `127.0.0.1`，不要混用。
- 飞书测试环境如果控制台不接受 `localhost`，可以全链路改用 `127.0.0.1:5173`（`FrontendBaseUrl`、两个平台回调、配置文件一起改）。
- 生产必须 HTTPS；两个平台后台的地址与配置文件必须逐字符一致。
- 如果前面还有反向代理/自定义路径，回调地址要按最终浏览器看到的 URL 填。

## 7. 安全与合规要求

### 7.1 数据最小化

- 只存 `Provider + ProviderUserId + UserId + 时间`。
- 不存第三方姓名、昵称、头像、邮箱、手机号、`tenant_key`、原始响应。
- 第三方 token 用完即弃；GitHub token 额外调用撤销接口。
- 日志不记录 `code`、`state`、token、secret；必要时只记录 provider、userId、结果、IP、UA。

### 7.2 OAuth 安全

- `state`：后端生成高熵随机值，加密 cookie 保存，回调比对，10 分钟过期。
- GitHub 使用 PKCE S256；飞书当前链路不支持 PKCE，用 state + 一次性 code + 后端 secret 补偿。
- 回调地址精确匹配，不使用 wildcard；生产 HTTPS。
- 不在 URL 中返回本站 token；callback 只回传 `status` / `returnUrl`，会话由后端设置。
- `returnUrl` 只允许本地路径，防止开放重定向。
- 绑定只允许已登录管理员发起；绑定意图放在加密 state cookie 中。
- 不按第三方邮箱自动关联账号；只认 `ProviderUserId` + 显式绑定。

### 7.3 平台与品牌

- 使用 GitHub / 飞书官方登录标识，不暗示官方背书。
- 仅用于本站管理员登录，不抓取、不转卖第三方数据。
- 如果站点有隐私说明，补充「第三方登录仅读取公开用户标识，不存储资料」。
- 飞书应用名称/图标/描述遵守企业应用规范；发布前经企业管理员审核。
- 遵守平台条款：GitHub 的 Terms of Service、Acceptable Use、Privacy Statement；飞书开放平台协议与企业数据安全要求。不得将第三方登录用于抓取、推广、冒充等用途。

### 7.4 第三方脚本

- 飞书扫码 SDK 从飞书 CDN 加载；如果后续给站点加 CSP，需要放行：
  - `script-src https://lf-package-cn.feishucdn.com`
  - `frame-src https://passport.feishu.cn`
- 只在登录页按需加载，不在全站引入。
- 监听 `message` 时必须用 SDK 的 `matchOrigin` / `matchData` 校验，不能直接 `eval` 或信任任意消息。

## 8. 我实现时会怎么用这些配置

1. 新增 `ExternalAuth` 配置节；`Enabled=false` 或缺少凭据时，登录页不显示对应入口。
2. 启动时校验：`Enabled=true` 但 Secret 缺失/过短，直接拒绝启动（与现有 `Jwt:SigningKey` 一致）。
3. 新增 `ExternalLogins` 绑定表（只含第 1.3 节的字段）和绑定/解绑接口。
4. 新增 provider 适配：
   - GitHub：授权 URL + PKCE、token 交换、`GET /user` 取 `id`、撤销 token。
   - 飞书：网页跳转走 v3；扫码按官方教程走旧 `passport` + `app_access_token` + `/authen/v1/oidc/access_token` + `user_info`。
5. 登录页：密码表单 + GitHub 按钮 + 飞书按钮 + 飞书扫码入口。
6. 后台配置页：仅 Admin 可进；显示绑定状态；绑定/解绑。
7. 回调：校验 state → 换 token → 取 `ProviderUserId` → 查绑定 → 签发本站会话；未绑定则回登录页提示。
8. 不自动注册、不存资料、不存第三方 token。

- [ ] 把非敏感值填入 `appsettings.Development.json` / `appsettings.Production.json` 的 `ExternalAuth` 节。
- [ ] 把两个 Secret 写入本地环境变量或 `.env`，不要提交。
- [ ] 告诉我「配置已填好」，并附上（非敏感的）App ID / Client ID / 回调地址 / 生产域名；**不要发 Secret**。

### 9.2 需要你拍板的小决策

1. **绑定权限**：只允许 Admin 绑定，还是 Author 也可以？
   - 当前按只允许 Admin 设计。
2. **生产域名**：`https://<你的域名>` 具体是什么？
   - 影响 `FrontendBaseUrl`、两个回调地址、GitHub/飞书后台配置。
3. **飞书 `open_id` 重建风险**：是否额外存 `union_id` 作为兜底？
   - 默认只存 `open_id`；如果担心以后删除重建飞书应用导致绑定失效，可以加存 `union_id`（仍是登录标识，不是资料）。
4. **飞书扫码链路**：默认按你给的官方教程走旧 `passport` + `/authen/v1/oidc/access_token` 链路；如果实测该端点不可用，再评估自建轮询。你无需现在决策，除非你明确要求全部走 v3。
