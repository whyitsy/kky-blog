## 0. 一句话与全貌

一个单体博客：Vue 3 SPA 负责展示与后台操作，ASP.NET Core 提供 REST API，
PostgreSQL 存数据（带中文分词做全文检索），Redis 承担缓存与分布式限流，
Nginx 容器做静态文件与反代，宿主机 Caddy 终结 TLS，全部跑在一台 2 核 2G 的 Ubuntu 上。

```
浏览器
  │  https://www.kkynet.site
  ▼
┌─ 宿主机 Caddy ──────────── 自动申请/续期证书，反代到 127.0.0.1:8080
  ▼
┌─ 容器 nginx:1.29-alpine ── 静态文件(dist) + /assets 长缓存 + SPA fallback
  │                           /api/** 反代 → webapi:8080（overwrite XFF）
  ▼
┌─ 容器 webapi (.NET 10) ─── 中间件管线 → 控制器 → 应用服务 → 仓储
  │                           缓存 / 限流 / 计数都过 Redis
  ▼
┌─ 容器 pgsql:18+zhparser ── 业务数据 + tsvector 生成列（中文全文检索）
└─ 容器 redis:7.4.11 ─────── 缓存（含空值哨兵、分布式锁）+ 限流令牌桶
```

## 1. 技术栈与选型理由

| 选择 | 理由 |
|---|---|
| **EF Core 10 + Npgsql** | 迁移即代码，随应用启动自动应用，个人项目不需要 DBA 流程；LINQ 覆盖 95% 的查询 |
| **PostgreSQL 而不是 MySQL** | 选它的**唯一决定性理由是 `tsvector` + `zhparser`**：中文全文检索不需要额外引入 ES |
| **不用 Elasticsearch / Meilisearch** | 单机 2G 内存，再跑一个 JVM 或独立检索服务不划算；博客量级（几千篇）PG 的 GIN 索引足够 |
| **JWT（HS256）自签** | 无状态，不需要额外的认证服务；`Microsoft.AspNetCore.Authentication.JwtBearer` 是框架包 |
| **PBKDF2** | `Rfc2898DeriveBytes.Pbkdf2` 就在 BCL 里（框架内置），零三方依赖，升级迭代次数不需要引包 |
| **ImageSharp 3.x** | 上传的位图转 WebP，省流量；纯托管实现，部署最简单 |
| **Nginx + Caddy 双层** | 容器内 Nginx 负责静态文件与反代（配置可控），宿主机 Caddy 负责证书 |
| **Docker Compose（不用 K8s）** | 单机、四容器、没有弹性伸缩需求 |
| **GitHub Actions + GHCR** | 公开仓库免费；镜像 tag = commit sha，天然不可变，回滚就是"再部署一次旧 sha" |

## 2. 项目结构原理

### 2.1 分层与依赖方向

```
Blog.Domain          ← 实体 + 仓储接口。零框架依赖（连 EF 都不引）
      ▲
Blog.Application     ← 业务服务、DTO、缓存键、字段长度、错误码。只依赖 Domain
      ▲
Blog.Infrastructure  ← EF Core / Npgsql / Redis / JWT / 文件 / 限流。实现 Application 的接口
      ▲
Blog.WebApi          ← Program.cs、控制器、中间件、健康检查、appsettings
```

依赖是**单向**的：`Domain` 不知道 EF，`Application` 不知道 HTTP。

两个具体体现：

- **`Post.SearchVector` 用影子属性声明**（`BlogDbContext.cs`）。`NpgsqlTsVector` 是 Npgsql 的类型，
  而 `Blog.Domain` 必须保持零框架依赖，所以这一列只存在于 Infrastructure 层，查询时用 `EF.Property` 访问。
- **`ICurrentUser` 在 Application，实现 `HttpCurrentUser` 在 Infrastructure**。业务服务不碰 `HttpContext`，
  因此 `PostService` 这类服务可以用 `Mock<ICurrentUser>` 单测（见 `PostServiceTests`）。

### 2.2 读写仓储分离

仓储接口刻意分成两套：

| 写侧 | 读侧 |
|---|---|
| `IPostRepository`、`ICategoryRepository`、… | `IPostQueryRepository`、`ICategoryQueryRepository`、… |
| 面向聚合：`Add/Update/Remove/GetById`，返回**被跟踪的实体** | 面向查询：直接返回 DTO，`AsNoTracking()`，可以尽情用投影/原生 SQL |
| 实现里是 EF 常规用法 | 实现里允许 `ts_rank` 这类原生 SQL，不受聚合边界约束 |

好处是读路径不用为了"返回实体"而多查几列，写路径也不用担心投影破坏跟踪。
`TaxonomyQueryRepository` 一个类同时实现 `ICategoryQueryRepository` 和 `ITagQueryRepository`
（两者查询形状一样），这是有意的复用。

### 2.3 DI 装配点

只有两个入口，都叫 `DependencyInjection`：

- `AddApplication()`：注册 8 个应用服务（全部 Scoped）。
- `AddInfrastructure(configuration)`：注册 DbContext、仓储、缓存提供者、限流器、JWT、文件存储、
  以及**启动期校验**（`DeploymentGuard.Validate`）。

`ICacheService` 的选择是一个工厂委托：`Enabled=false` → `NullCacheService`（完全旁路）；
`Provider=Redis` → `RedisCacheService`；否则 → `MemoryCacheService`。
**用一个接口 + 三种实现**，业务代码里没有任何 `if (redis)` 分支。

### 2.4 配置分层

```
Blog.WebApi/appsettings.json              ← 只有日志级别与 AllowedHosts
Blog.WebApi/appsettings.Development.json  ← 开发连接串、开发 JWT 密钥、本地 Redis
Blog.WebApi/appsettings.Production.json   ← 生产连接串与密钥**故意不在这里**，只有结构配置
环境变量                                    ← 覆盖一切（12-Factor）
```

生产的密钥只有两条路进来：`ConnectionStrings__DefaultConnection` 与 `Jwt__SigningKey`
（双下划线是 .NET 的层级分隔符）。`.env.example` 是模板，真实 `.env` 被 `.gitignore` 的
根路径规则 `/.env` 忽略（不会误伤已入库的 `Blog.FrontEnd/.env`）。

> `appsettings.Production.json` 存在的原因是踩过的坑：在它出现之前，
> `Cache` / `FileStorage` / `RateLimit` 三节**只存在于 Development 文件里**。
> 生产环境于是 `Cache` 走默认 Memory，而 `RateLimit` 变成"开关是 true、规则是空数组"
> = **限流完全不生效，但看起来一切正常**。这类"开关开着却没在工作"的配置缺陷最难发现，
> 所以现在两套文件的这三节保持一致，只在必要处不同（路径绝对化、CORS 留空、Redis 用服务名）。

## 3. 后端设计要点

### 3.1 启动管线

`Program.cs` 是顶层语句，整条管线按下面的顺序装配。**顺序本身就是设计**，几处关键注释解释了原因：

| # | 调用 | 为什么在这个位置 |
|---|---|---|
| 1 | `Log.Logger = CreateBootstrapLogger()` | 在 DI 容器建好之前也要能记日志，否则"启动时崩了"什么都看不到 |
| 2 | `UseSerilog(...)` | 控制台 + `logs/blog-.log` 按天滚动、保留 30 天 |
| 3 | `AddControllers()` + `InvalidModelStateResponseFactory` | 接管 `[ApiController]` 的默认 400，让它输出统一响应体（见 3.2 出口③） |
| 4 | `AddOpenApi()` | 仅 Development 下 `MapOpenApi()` 暴露 |
| 5 | **读取 `Jwt:SigningKey` 并校验长度 ≥ 32 字节** | 不满足直接 `throw`，应用拒绝启动 |
| 6 | `AddAuthentication().AddJwtBearer(...)` | `ClockSkew = 30s`（默认 5 分钟会让"刚过期"的 token 还能用）；`OnChallenge`/`OnForbidden` 写统一响应体 |
| 7 | `AddAuthorization(...)` 三个策略 | `AdminOnly` / `ContentWriter` / `Authenticated`，每个都叠加 `RequireResolvedUserRequirement` |
| 8 | `AddCors("Frontend")` | 来源读 `Cors:Origins`，生产是空数组（同源部署，不会触发 CORS） |
| 9 | `AddApplication()` / `AddInfrastructure()` / `AddBlogHealthChecks()` | 业务装配 |
| 10 | `app.UseSerilogRequestLogging(...)` | ⚠️ **必须在 `ExceptionHandlingMiddleware` 外层**（即先注册） |
| 11 | `app.UseMiddleware<ExceptionHandlingMiddleware>()` | 见 3.2 |
| 12 | `app.UseStatusCodePages(...)` | 兜住**路由阶段**的失败（出口④） |
| 13 | `app.UseMiddleware<RateLimitingMiddleware>()` | 限流在认证之前：被限流的请求不该先花一次身份解析 |
| 14 | `app.UseCors("Frontend")` | 必须在认证之前 |
| 15 | `app.UseAuthentication()` | |
| 16 | `app.UseMiddleware<CurrentUserResolutionMiddleware>()` | 需要先有 `ClaimsPrincipal`，所以排在认证之后 |
| 17 | `app.UseAuthorization()` | 用第 16 步写入的解析结果判 401/403 |
| 18 | `MapControllers()` + `MapGet("/")` + `MapBlogHealthChecks()` | |
| 19 | `dbContext.Database.Migrate()` | 启动时自动应用迁移（在 `app.Run()` 之前，同步执行） |
| 20 | `app.Run()`，外层 `try/catch` | 捕获时排除 `HostAbortedException`（`dotnet ef` 正常中止宿主会抛它），否则记 `Fatal` |

第 10 步那个顺序值得单独说：如果请求日志中间件注册在异常处理**内层**，
`BusinessException`（比如"分类名重复"）会先冒泡穿过它，日志里记录到的是 **500 + 完整堆栈**，
而客户端实际收到的是 400/404/409。日志与事实不符，且正常的业务失败会刷满 ERR，
把真正的故障淹掉。现在按状态码分级：5xx = Error，4xx = Warning，其余 Information。

### 3.2 统一响应体：`{code, message, data}` 的八条出口

承诺是"**所有**接口（含错误）都返回同一个结构"，前端 `http.ts` 只需要一套解析逻辑。
要真正做到"无条件成立"，得把八条出口全部接管：

| # | 出口 | 由谁接管 | 结果 |
|---|---|---|---|
| ① | 业务失败 | `ExceptionHandlingMiddleware` 捕获 `BusinessException` | 业务码 → HTTP 状态码映射 |
| ② | 乐观锁冲突 | 同上捕获 `DbUpdateConcurrencyException` | 409 + 4090 |
| ③ | Action 参数校验失败 | `ApiBehaviorOptions.InvalidModelStateResponseFactory` | 400 + 4001（默认会输出 RFC 7807 的 `{type,title,status,errors}`） |
| ④ | **路由阶段**失败（约束不匹配、路径不存在） | `UseStatusCodePages` 兜底空响应体 | 404/405 + 统一体 |
| ⑤ | 未认证 | JwtBearer `OnChallenge`（`context.HandleResponse()` 阻止默认空响应） | 401 + 4010 |
| ⑥ | 未授权 | JwtBearer `OnForbidden` | 401 或 403（见 3.3） |
| ⑦ | 触发限流 | `RateLimitingMiddleware` | 429 + 4091 + `Retry-After` |
| ⑧ | 未处理异常 / 字段超长 | `ExceptionHandlingMiddleware` 的兜底 catch | 500 + 5000 / 400 + 4001 |

> **两个有意例外**：`GET /`（返回 `{name,status}` 的匿名对象）与 `GET /health`
> （返回纯文本 `Healthy`/`Unhealthy`）不走统一响应体。前者只是"服务活着吗"的探活，
> 后者刻意不给匿名访问者任何内部细节——它们的契约分别由代码本身和容器 HEALTHCHECK 固定。

出口④是最容易被漏掉的一条：`{id:guid}` 约束不匹配时，请求**根本没到中间件**，
框架直接写一个空 body、无 Content-Type 的 404。修复前的实测是
`GET /api/posts/not-a-guid` 与 `GET /api/totally/wrong/path` 都返回 `Content-Type='' Body=<空>`。
`UseStatusCodePages` 只接管"状态码 ≥ 400 且 `Response.HasStarted == false`"的响应，
所以不会覆盖①⑤⑥⑦已经写好的内容。

出口⑧里的 `PostgresException` SQLSTATE `22001`（字符串超长）是**兜底兜底**：
正常路径上应用层应该先用 `FieldLimits` 拦下（见 3.7），这里只是保证万一漏了某个字段，
用户看到的是"内容太长请缩短"而不是"服务器内部错误"，同时在日志里留一条 Warning
（"说明 Application 层漏了校验"）。

错误码表（`ErrorCodes.cs`），与前端 `http.ts` 的 `ErrorCode` 常量一一对应：

```
0     成功            4010  未认证（缺 token / 无效 / 过期 / 账号停用）
4001  参数校验失败      4030  无权限（角色不足 / 越权访问他人资源）
4002  业务规则不满足    4040  资源不存在
4003  资源重复         4090  乐观锁并发冲突
                      4091  触发限流
                      4130  请求体过大
                      5000  系统异常
```

映射规则：`4010→401`、`4030→403`、`4040→404`、`4090→409`、`4091→429`、`4130→413`，
**未列出的业务码一律落 400**。这条"兜底落 400"的规则和出口④的反向映射
（状态码 → 业务码）保持一致，不为好看而新增错误码。

### 3.3 认证与授权

#### 为什么不用 Refresh Token

只有 Access Token，30 分钟（`Jwt:AccessTokenMinutes`）。代价是"无状态 = 无法主动失效"：
注销、改密码、停用账号之后，旧 token 在到期前**签名依然有效**。

补偿方案是 `User.TokenVersion`：

- 签发时把当前的 `TokenVersion` 写进自定义 claim `tv`；
- 每个带 token 的请求，`CurrentUserResolutionMiddleware` 拿 claim 里的 `tv` 和库里的值比对；
- 注销 / 重置密码 / 停用账号都会 `TokenVersion++`（见 `User.cs` 的 `LogoutAllDevices` / `ResetPassword` / `SetActive`）；
- 变更之后**立刻**调 `ICurrentUserCache.InvalidateAsync` 清缓存（TTL 5 分钟只是"万一忘了失效"的兜底）。

claim 结构：

```
sub      账号 Id
role     Admin / Author（用 ClaimTypes.Role，可以直接喂给 [Authorize(Roles=...)] 和策略）
tv       TokenVersion
authorId 关联的署名作者 Id（可空）
jti      随机 Guid（便于将来做黑名单）
```

#### 三个授权策略

| 策略 | 要求 | 用在哪 |
|---|---|---|
| `AdminOnly` | `RequireRole("Admin")` + `RequireResolvedUserRequirement` | 分类/标签/专栏/站点配置/账号管理、作者增删 |
| `ContentWriter` | `RequireRole("Admin","Author")` + 同上 | 文章增改发删、文件上传、改自己的作者资料 |
| `Authenticated` | 只要 `RequireResolvedUserRequirement`（不限角色） | `/api/auth/me`、`/api/auth/logout` |

第三个策略的存在有具体原因：这两个端点的语义是"只要登录"，但如果写裸 `[Authorize]`，
它会落到 `DefaultPolicy`，而改 `DefaultPolicy` 会影响所有兜底授权。单独给一个具名策略更稳。

#### 那个"危险的空档"（`RequireResolvedUser.cs`）

中间件在校验不通过时**刻意不返回 401**，只是不往 `HttpContext.Items` 里写当前用户。
这是为了让"公开接口 + 一个过期 token"仍然能正常浏览（带 token 逛首页不该被拦）。

但这样就出现了一个空档：一个**已被作废**的 token，在 `[Authorize]` 看来签名有效、没过期，
于是端点拿着"解析结果为空"的身份继续执行。实测（修复前）：
`GET /api/posts/{已发布id}/readonly` 在注销之后**仍然返回 200 + 文章数据**。

补法是把判断放到**授权阶段**：所有策略都叠加 `RequireResolvedUserRequirement`，
处理器只读 `ICurrentUser.IsAuthenticated`（背后就是中间件写的那份解析结果）。
于是"凡是标了 `[Authorize]` 的端点，都要求身份真的解析成功"，作废即 401。

#### 401 还是 403

框架的 `PolicyEvaluator` 按"用户是否已认证"二选一。而本项目的 token 是**无状态 JWT**，
注销/改密/停用后框架仍认为"已认证"，于是授权失败一律走 `Forbid` → **403**。
但"注销后的旧 token"语义上是**凭据无效**，应该是 401，客户端也据此才会清登录态、跳登录页。

所以 `OnForbidden` 里会读 `HttpContext.Items` 的 `RejectionKey`：

```
有 RejectionKey（UserNotFound / Inactive / TokenVersionMismatch）→ 401 + 4010「登录状态已失效」
没有 RejectionKey（身份有效但角色不足）                        → 403 + 4030「无权限执行该操作」
```

那个 `Items` 是"身份为什么被拒"的**唯一事实来源**，`RequireResolvedUserHandler` 里
`context.Fail(...)` 带出去的字符串只用于排障，不参与最终判定。

#### 密码哈希

```
存储格式：pbkdf2-sha512${iterations}${base64(salt)}${base64(hash)}
参数：    SHA512 / 210,000 次迭代（OWASP 建议量级）/ 每用户 16 字节随机盐 / 32 字节输出
校验：    CryptographicOperations.FixedTimeEquals（恒定时间，防时序攻击）
```

格式是**自描述**的，所以校验时用的是"这条记录里记的迭代次数"而不是当前默认值：
将来提高默认迭代次数不会让老密码失效，登录成功时用 `NeedsRehash` 静默升级。
解析失败一律 `return false`（不抛异常），避免把格式细节变成可用的探测信号。

### 3.4 限流

`RateLimitingMiddleware` + 令牌桶。只对 `/api` 前缀生效，规则完全来自配置：

| 规则 | 路径 | 方法 | 容量（突发） | 速率（持续） |
|---|---|---|---|---|
| `search` | `/api/posts/search` | GET | 20 | 2 /s |
| `write` | `/api` | POST | 30 | 2 /s |
| `default` | `/api` | 任意 | 120 | 20 /s |

匹配是**顺序取第一条命中的规则**，所以 `search` 必须排在 `default` 前面；
桶 key 是 `blog:ratelimit:{规则名}:{粒度}`，粒度为 `ip`（默认）/ `global` / `endpoint`。

**原子性靠 Lua**（`RedisTokenBucketLimiter`）：`HMGET` 取 tokens/ts → 按流逝时间补令牌
（`min(capacity, tokens + elapsed*rate)`）→ 够就扣 1，不够就算 `retryAfter`
→ `HMSET` 写回 → `PEXPIRE capacity/rate*2000`（闲置两倍填满时间后自动过期，避免 key 无限增长）。
整段脚本在 Redis 里是原子的，多实例共享同一个桶，不会出现"读了再写"的竞态。

**降级链**：Redis 抛 `RedisConnectionException` / `RedisTimeoutException` / `InvalidOperationException`
时，按 `RateLimit:FallbackToMemory` 决定降级到内存桶还是直接放行。响应头：
`X-RateLimit-Remaining`（放行时）、`Retry-After`（拒绝时，单位秒，至少 1）。

#### 这个中间件踩过的最大一个坑：信任边界

`GetClientIp()` 取 `X-Forwarded-For` 的**第一段**（`Split(',')[0]`）。
而 Nginx 侧原先用的是官方范例 `proxy_add_x_forwarded_for`，它的行为是
**保留客户端自己发的 XFF，再追加真实 IP**，于是头变成 `"<客户端伪造的IP>, <真实IP>"`——
第一段完全由客户端控制。

结果：每次请求伪造一个新的 XFF，每个请求都拿到一个全新的令牌桶，**限流被完全绕过**。
本地实测对照（`deploy/README.md` 有完整记录）：

| 测试 | 修复前 | 修复后 |
|---|---|---|
| 正常请求 28 次 | 第 21 次起 429 ✅ | 同左 ✅ |
| 每次伪造不同的 XFF | **0 次 429**（完全绕过）❌ | **26 次 429** ✅ |

修复是让 Nginx **覆盖**整个头：`proxy_set_header X-Forwarded-For $remote_addr;`。
前提是"Nginx 是唯一入口"（本项目 `webapi` 不对外发布端口，成立）。
若将来前面加 CDN 或云 LB，就不能退回追加写法，而要改用
`ngx_http_realip_module` 信任上游网段，或者干脆在应用侧用
`ForwardedHeadersMiddleware` + `KnownProxies` 把信任边界表达在代码里。

### 3.5 缓存

#### key 规范

```
blog:{模块}:{操作}:v{版本}:{固定维度}:{可选 hash}
例：blog:posts:list:v1:p1s10:c-t-col-a-o-u0:k3F2A...:u0
    blog:posts:detail:v1:{guid}
    blog:site:config:v1:-
    blog:auth:user:v1:{userId}
```

几个约定：

- 固定前缀 `blog:`，便于按前缀失效，也避免与共用 Redis 的其他应用冲突；
- `v{版本}` 用于"缓存结构不兼容变更"时整体失效——改版本号即可，旧 key 没人访问、靠 TTL 自然消失，
  不需要 `SCAN` 清理；
- 缺省维度用 `-` 占位，**保持段数固定**，排查时好读；
- 关键词不可枚举且可能很长，做 SHA256 取前 16 位，避免特殊字符和超长内容污染 key。

#### TTL 一览

| 内容 | TTL | 位置 |
|---|---|---|
| 文章列表 | 5 分钟 | `PostService.ListCacheTtl` |
| 文章详情 | 10 分钟 | `PostService.DetailCacheTtl` |
| 归档 | 30 分钟 | `PostService.ArchiveCacheTtl` |
| 分类 / 标签 | 30 分钟 | `CategoryService` / `TagService` |
| 站点配置 | 1 小时 | `SiteService.ConfigTtl` |
| 站点统计 | 10 分钟 | `SiteService.StatsTtl` |
| 账号认证快照 | 5 分钟 | `CurrentUserCache.Ttl` |
| 空值哨兵 | 2 分钟 | `Cache:NullTtl` |

#### 三个经典问题都在 `RedisCacheService` 里处理了

- **穿透**：空结果写哨兵 `∅`，TTL 用 `NullTtl`（比正常 TTL 短）。
  唯一的例外是账号缓存，它传 `cacheNull: false`——因为"账号不存在"不能缓存，
  否则刚被软删的账号会在 `NullTtl` 内持续被判为不存在，或者重建账号后仍然判为不存在。
- **击穿**：`GetOrCreateAsync` 里用 `LockTakeAsync` 抢分布式锁，**只有一个请求回源重建**；
  抢不到锁的直接回源（短等待，不阻塞）。拿到锁后**再查一次**（双检），可能已经被别人重建好了。
- **雪崩**：`ApplyJitter` 给 TTL 加 ±20% 随机抖动，避免同一批 key 同时过期。

失效策略是"**前缀失效 + 主动失效**"：文章的任何写操作都会
`RemoveByPrefixAsync("blog:posts:")` 并顺手删掉 `blog:stats:summary`；
账号相关操作主动删掉 `blog:auth:user:{id}`。

`RemoveByPrefixAsync` 用的是 `server.Keys(pattern:)`，这在生产环境是有风险的操作（会遍历键空间）。
个人博客量级可以接受；如果 key 数量上去了，应该改成维护一个 key 集合（Set）来精确删除。

**任何 Redis 故障都不向调用方抛异常**：连接不上、超时、反序列化失败，一律记 Warning 后
返回 `default`，业务逻辑就当缓存没有命中，直接回源。缓存永远不该成为可用性的单点。

### 3.6 文件与媒体安全

这块是整个项目里"安全代码"密度最高的地方。

#### 上传（`FilesController.Upload` + `LocalFileStorageService.SaveAsync`）

- 需要 `ContentWriter` 策略（Admin 或 Author）。**匿名开放等于让任何人往磁盘塞文件**。
- 扩展名白名单：`.png .jpg .jpeg .gif .webp .ico .mp4 .webm .pdf .zip`。
- 落盘路径 `{Root}/yyyy/MM/{guid:N}{ext}`，文件名由服务端生成，**不使用用户提供的文件名**。
- 大小：`FileStorage:MaxFileSize` = 10MB，控制器上还有 `[RequestSizeLimit(50MB)]` 作为外层兜底，
  Nginx 侧 `client_max_body_size 12m`。
- 位图先过 `IImageOptimizer` 转 WebP（质量 82，最长边 2560，最多 4000 万像素），
  转换失败或不该转的一律原样保存——**上传不能因为优化失败而失败**。
- 返回 `{url, storedBytes, originalBytes, converted}`，前端可以显示压缩效果。

#### 为什么白名单里没有 `.svg`

SVG 可以内嵌 `<script>`，而本服务的文件读取接口用 `File(stream, contentType)` **同源**下发。
一个拥有 `ContentWriter` 的账号（作者就够）上传恶意 SVG，再把
`/api/files/xxx.svg` 发给管理员，管理员**直接打开这个链接**时脚本就在站点源上执行——存储型 XSS。
（注意区分：`<img src="x.svg">` 里的 SVG 是"被动图像"，脚本不执行；风险在于把它当**顶层文档**导航过去。）

`ContentTypes` 表里也刻意没有 `.svg`，这是第二层兜底：万一有人手工把 svg 丢进媒体目录，
它只会被当作 `application/octet-stream` 下载，不会内联渲染成文档。
将来真需要矢量图，正确做法是**先转成位图再入库**。

#### 路径穿越（`TryResolveSafePathIn`）

读文件的路径来自 URL（`/api/files/{**path}`），是用户可控输入。三道检查：

1. 拒绝含 `..` 的路径，拒绝绝对路径（`Path.IsPathRooted`）；
2. `Path.GetFullPath` 归一化之后，**必须严格位于根目录之下**；
3. 比较时用 `rootFull + Path.DirectorySeparatorChar` 做前缀，避免 `/media-seed` 被 `/media` 前缀匹配到。

上传目录与只读种子目录（`media-seed`，随仓库分发的默认头像）**走同一套校验**，
种子目录不会成为绕过点。实测 `/api/files/....//....//etc/passwd` 到达应用后返回 404。

#### 媒体地址白名单（`MediaPath.cs`）

作者头像、文章封面、站点 Logo、首屏背景图这四个字段本质是"一个图片地址"。
改造前它们是自由文本框，后端原样存、原样下发，于是任何能调写接口的人都能塞进：

```
https://evil.com/x.png        外链图片：访客 IP/UA 泄露给第三方，还会触发混合内容告警
//evil.com/x.png              协议相对 URL，同上但更隐蔽
javascript:alert(1)           今天只进 <img src> 看似无害，哪天被复用到 <a href> 就是 XSS
data:image/svg+xml;base64,... data URI，SVG 内部可携带脚本
```

现在是白名单：只认 `/api/files/` 前缀 + 受限字符集（字母数字 `/ . - _`）。
**刻意不写黑名单**（禁止 `http:` / `javascript:` / `data:`），因为黑名单只能挡住已经想到的写法。

形状约束还有三条：不能以 `/` 开头（避免 `/api/files//...` 的归一化歧义）、
不能以 `/` 结尾（目录永远不可能是文件）、不能含 `..` 或 `//`。
长度上限取 `FieldLimits.AuthorAvatar` = 200，即**所有目标列里最小的那个**
（`Authors.Avatar` 是 varchar(200)，`Posts.CoverImage` 是 varchar(500)）——
取最小值才能保证"通过白名单的值一定能存进任何一个目标列"，否则会出现
"过了白名单、却在写头像时撞数据库约束"这种表现为 500 的怪事。

读写策略**故意不同**：写入走 `Validate`（非法即拒），读取走 `ParseList`（对历史数据宽容），
避免一次校验规则升级就把老数据读崩。

#### 下载接口的两个细节

- `Cache-Control: public,max-age=86400` **只在命中文件时下发**。之前用 `[ResponseCache]` 标注 action，
  会给"文件不存在"的 404 也盖上 `max-age=86400`，于是浏览器把 404 缓存一整天，
  文件补回来之后用户还是看到空白背景，必须强刷。
- 失败路径**抛异常**而不是 `return NotFound(...)`。后者会得到"HTTP 404 + body.code 4040"，
  同一个响应里两处表达"哪里错了"，客户端要同时看两个地方。抛异常后由中间件统一产出"404 + {code:4040}"。
  命中文件仍然直接 `return File(...)`（流式响应不能被异常打断），并开启 `enableRangeProcessing`。

### 3.7 数据模型与数据库

#### 表

| 表 | 说明 |
|---|---|
| `Posts` | 文章。标题/正文/摘要/封面/发布时间/阅读数/字数/分类/作者/创建者账号 + `SearchVector` 生成列 |
| `Authors` | 署名作者（与登录账号**分离**）。姓名/邮箱/头像/简介 |
| `Users` | 登录账号。邮箱/密码哈希/角色/是否启用/关联 Author/最近登录/`TokenVersion` |
| `Categories`、`Tags` | 分类与标签，`Posts` 与 `Tags` 是多对多 |
| `Collections` + `PostCollections` | 专栏与"文章↔专栏"连接表（连接表带专栏内排序） |
| `SiteConfigs` | 键值配置（站点名、副标题、Logo、首屏打字机文案 JSON、建站日期…） |
| `SocialLinks` | 社交链接（图标 key、URL、排序、是否可见） |

`Author` 与 `User` 分离是刻意的：署名是内容属性（可以没有账号），
登录是凭据属性（可以有多个账号指向同一个署名）。文章的**归属校验只认 `CreatedByUserId`**
（创建这篇文章的账号），不认 `AuthorId`——否则"作者 A 把自己的署名改成 B"就能把文章送出去。

#### 四个通用约定

**软删除**：`BaseEntity` 有 `IsDeleted` / `DeletedAt`，每个实体配 `HasQueryFilter(e => !e.IsDeleted)`，
业务代码不需要到处写 `Where(!IsDeleted)`。

**过滤唯一索引**：软删除之后同一邮箱/同一 slug/同一分类名要允许复用，所以唯一索引写成
`HasIndex(e => e.Email).IsUnique().HasFilter("\"IsDeleted\" = false")`。

**乐观锁**：`Version` 列。删除/更新接口要求客户端回传 `version`（`[FromQuery] int version`），
服务端 `ApplyOptimisticVersion(post, version)` 生成 `UPDATE ... WHERE "Version" = @expected`，
affected rows = 0 就抛 `DbUpdateConcurrencyException` → 409 + 4090。
`ValidateVersion` 拒绝版本号 ≤ 0，避免"没传版本号就等于跳过并发控制"。

**时间**：全部用 `DateTimeOffset`（带偏移），存 UTC。

#### 中文全文检索

`Posts.SearchVector` 是一个**生成的 `tsvector` 列**（`stored: true`），表达式：

```sql
setweight(to_tsvector('chinese', coalesce("Title",   '')), 'A') ||
setweight(to_tsvector('chinese', coalesce("Summary", '')), 'B') ||
setweight(to_tsvector('chinese', coalesce("Content", '')), 'C')
```

标题权重 A、摘要 B、正文 C，所以搜出来的排序会自然偏向标题命中的文章。查询侧用
`plainto_tsquery('chinese', keyword)` 配合 `@@` 匹配，把 `ts_rank` 作为**投影列**算出来，
再按 rank 排序（`PostQueryRepository` 里有注释解释为什么不直接在原生 SQL 里 `ORDER BY ts_rank`）。

#### `chinese` 检索配置缺 `j,q` 的静默故障

这是本项目最值得记录的一个坑，细节在 `deploy/README.md`。

- 项目用的社区镜像 `mixdeve/postgres-zhparser:18` 自带的 entrypoint 脚本会建 `chinese` 配置，
  但它只映射 `n,v,a,i,e,l`，**少了 `j`（简称）和 `q`（量词）**。
- 而迁移 `20260910205225_AddAuthCollectionsAndFts` 里创建配置的那段 SQL 是"**配置不存在才创建**"，
  镜像脚本一旦先跑，那段就整体跳过，于是 `j,q` 永远补不上，**而且不报任何错**。
- 后果是实测的：没有映射的 token 类型会被 `to_tsvector` 直接丢弃、不进索引。

```sql
-- 缺 j,q：量词「篇」「个」消失
SELECT to_tsvector('chinese','一篇文章 五个参数');   -- '参数':2 '文章':1
-- 补上后：
SELECT to_tsvector('chinese','一篇文章 五个参数');   -- '个':3 '参数':4 '文章':2 '篇':1
```

解法是新增迁移 `20260918174440_EnsureChineseConfigTokenMappings`：

1. `DO` 块自己判存在性后 `ADD MAPPING FOR j,q`——PostgreSQL **没有**
   `ADD MAPPING IF NOT EXISTS` 语法（实测 PG18 报 `42601`）；
2. 补完映射后**重写一次 `Posts`**。因为 `SearchVector` 是生成列，只在行写入时计算，
   改 `pg_ts_config_map` 不会让 PostgreSQL 重算任何生成列；
3. 重写语句必须 `SET` **生成表达式真正引用的列**（`"Title"`,`"Summary"`,`"Content"`）。
   ⚠️ 写成 `SET "Id"="Id"` 语句会报 `UPDATE 1`，但 `SearchVector` 原封不动，**完全静默**；
4. 只在"本次真的补了映射"时才重写：全新库不进这个分支，已带 `j,q` 的库也不进。

**为什么不能改老迁移**：EF 按迁移 ID 记录已应用的迁移，对已经上线的库改老迁移内容不会有任何效果
（它已被跳过），所以必须新增一条。

**为什么不挂载 `deploy/postgres-init/`**：配置的权威来源必须只有一个。
同时保留"挂载脚本"和"迁移"两条路径，将来改映射时很容易只改一处，另一处静默保持旧行为——
这正是上面那个故障模式本身。顺带的好处是 `pg_ts_config` 是**按库**存在的，
在已有实例上 `CREATE DATABASE` 建出的新库里没有 `chinese` 配置，挂载脚本帮不上忙，
而迁移每次都会在该库上执行。

CI 里有一条专门的回归断言（在测试**之后**跑，因为迁移由应用启动时执行）：
断言映射恰好是 `a,e,i,j,l,n,q,v`，并端到端确认量词确实进了索引。

#### 迁移策略

- 迁移文件在 `Blog.Infrastructure/Persistence/Migrations/`，共 5 条：
  `InitCreate` → `AddAuthCollectionsAndFts` → `FixSeedAuthorAvatar` → `ExtendPostSummaryLength`
  → `EnsureChineseConfigTokenMappings`。
- 应用启动时自动 `Database.Migrate()`。
- 设计期工厂 `BlogDbContextFactory` 读环境变量 `BLOG_CONNECTION`，
  与集成测试夹具**同名同义**，CI 里只设一次，不会出现两处凭证悄悄漂移。
- **回滚不含 schema**。旧镜像不会把表结构改回去，所以表结构变更只能自己想清楚再上。

### 3.8 配置与"失败前置"

这个项目有一个贯穿性的取向：**宁可在启动时崩，也不要带着错误配置静默运行**。
一共四处：

| 检查 | 触发条件 | 位置 |
|---|---|---|
| JWT 签名密钥 | 缺失或长度 < 32 字节 → 抛异常，拒绝启动 | `Program.cs` |
| 部署拓扑 | `InstanceCount > 1` 或 `RequireRedis = true`，但缓存不是 Redis → 拒绝启动 | `DeploymentGuard.Validate` |
| 迁移未应用 | `/health` 返回 Unhealthy（容器编排会拒绝把流量导进来） | `DatabaseHealthCheck` |
| 数据库字段超长 | 兜底降级为 400 而不是 500，同时记 Warning 提示"应用层漏了校验" | `ExceptionHandlingMiddleware` |

`DeploymentGuard` 的理由写得最直白：多实例下每台各自用内存缓存和内存令牌桶，
**限流阈值会被放大到"配置值 × 实例数"**，等于形同虚设；而缓存不共享会让 DB 压力翻倍。
这类问题靠运行期"静默降级"极难排查，所以把"部署拓扑"当成运维必须**显式声明**的输入，
而不是让代码去猜。

镜像里的配置注入点（`deploy/webapi.Dockerfile`）：

```dockerfile
ENV ASPNETCORE_ENVIRONMENT=Production \
    ASPNETCORE_HTTP_PORTS=8080 \
    VERSION=${VERSION} GIT_SHA=${GIT_SHA} BUILD_TIME=${BUILD_TIME}
```

`ASPNETCORE_HTTP_PORTS=8080` 用非特权端口，是为了让非 root 用户也能绑定。

#### 配置节速查

| 节 | 键 | 作用 | 默认 |
|---|---|---|---|
| `ConnectionStrings` | `DefaultConnection` | Npgsql 连接串（生产必须环境变量注入） | 仅 Development 有 |
| `Jwt` | `SigningKey` / `Issuer` / `Audience` / `AccessTokenMinutes` | 签名密钥（≥32 字节，否则拒绝启动）/ `blog-api` / `blog-frontend` / 30 | 生产**无此节**，全走环境变量 |
| `Cache` | `Enabled` / `Provider` / `RedisConnection` / `NullTtl` / `LockWaitTimeout` / `TtlJitterRatio` | 缓存总开关 / `Memory`\|`Redis` / 连接串 / 空值哨兵 2min / 内存锁等待 3s / 抖动 ±20% | `true` / `Memory` / `localhost:6379` |
| `RateLimit` | `Enabled` / `FallbackToMemory` / `Rules[]` | 限流开关 / Redis 故障是否降级内存桶 / 规则（`Name` `PathPrefix` `Method` `Granularity` `Capacity` `TokensPerSecond`） | 规则见 3.4 |
| `FileStorage` | `Root` / `SeedRoot` / `MaxFileSize` | 上传目录（生产绝对路径 `/app/media`）/ 只读种子回退目录 / 10MiB | `media` / `media-seed` / 10MB |
| `FileStorage:ImageOptimization` | `Enabled` / `WebpQuality` / `MaxDimension` / `MaxPixels` / `ConvertExtensions` | WebP 转换 / 82 / 2560 / 4000 万像素（防解压炸弹）/ `.png,.jpg,.jpeg` | 见左 |
| `Cors` | `Origins[]` | 开发 `["http://localhost:5173"]`，生产空数组（同源不触发） | `[]` |
| `Deployment` | `InstanceCount` / `RequireRedis` | 部署拓扑声明，`DeploymentGuard` 据此做启动校验 | `1` / `false` |
| `Logging` / `AllowedHosts` | | 日志级别 / `*` | |

两点值得记下来：

- **三个 appsettings 都是 JSONC**（带 `//` 注释），.NET 的配置提供程序接受，
  但 `jq` 这类严格 JSON 工具会解析失败——想用命令行读配置就别指望它。
- `appsettings.Development.json` 里的 `"//SigningKey"` **是一个真实存在的配置键**
  （全名 `Jwt://SigningKey`），只是内容为说明文字。它不是注释，只是用了"看起来像注释"的命名。


### 3.9 可观测性

| 能力 | 实现 |
|---|---|
| 结构化日志 | Serilog，控制台 + `logs/blog-.log` 按天滚动、保留 30 天（挂 `logs` 卷持久化） |
| 请求日志 | `UseSerilogRequestLogging`，模板带耗时；按状态码分级（5xx=ERR / 4xx=WRN） |
| 慢查询 | `SlowQueryInterceptor`（EF 拦截器），阈值 **500ms**，命中时把完整 SQL 写进 Warning 日志 |
| 健康检查 | `GET /health`：能连上 + `zhparser` 扩展在 + `chinese` 配置在 + **真的能分词** + 迁移全部应用；Redis 仅在启用时检查 |
| 版本信息 | `GET /api/version`：`{version, commit, builtAt}`，匿名可访问 |
| OpenAPI | 仅 Development 下 `MapOpenApi()` |

两个细节：

- **`/health` 对外只回 `Healthy` / `Unhealthy` 纯文本**。数据库地址、异常信息、
  依赖拓扑只写日志，不进响应。因为 `/health` 通常对编排系统和负载均衡开放，
  在响应里说清"哪个依赖挂了、报什么错"等于向匿名访问者泄露内部结构。
- **健康检查要真的执行一次 `to_tsvector('chinese', ...)`**，而不是只查
  `pg_extension`——只查扩展查不出"检索配置被删"这种情况。

`/api/version` 的版本号来源是**唯一权威路径**：CI 用 `--build-arg` 注入，
Dockerfile 的 runtime 阶段落到 `ENV` 并写一份 `/app/version` 供人工 `cat`，
运行期 `BuildInfoProvider` 读环境变量 `VERSION` / `GIT_SHA` / `BUILD_TIME`。

三个值的兜底规则：

| 字段 | 取不到时 | 为什么 |
|---|---|---|
| `version` | `"unknown"` | 刻意不用数字，避免被误认成真实版本号 |
| `commit` | 空串（字段保留） | 本地构建本来就没有 SHA，保留字段让调用方判断"未知" |
| `builtAt` | 当前时间（`O` 格式） | 空串会被当成解析失败，而"进程什么时候起来的"同样有排障价值 |

⚠️ **`Directory.Build.props` 里的 `0.0.0-local` 不会出现在 `/api/version` 里**。
它只进程序集元数据，而 `BuildInfoProvider` **刻意不读程序集版本**
（刻意不去读 `Assembly.GetEntryAssembly()`：在单元测试宿主里它返回的是**测试运行器**的程序集，
这个兜底在测试里根本验证不了，而"验证不了的兜底"等于没有）。
两处注释（props 文件 vs provider）措辞不一致，**实际行为以 provider 为准**：
本地 `dotnet run` 看到的是 `unknown`，要知道真实版本号就去容器里 `cat /app/version`。

只发布 `nginx` 的端口。`pgsql` / `redis` 刻意不映射到宿主机，两个原因：

需要直连时用 `docker compose exec pgsql psql -U kky -d blog_stage2`。

### 4.2 两个应用镜像

**`deploy/webapi.Dockerfile`**（多阶段）

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build        # 阶段 1：约 1GB
  COPY Blog.Domain/Blog.Domain.csproj            Blog.Domain/          # ← 先只复制 csproj
  ...                                            ...
  RUN dotnet restore Blog.WebApi/Blog.WebApi.csproj                     # ← 依赖层可缓存
  COPY Blog.Backend/ ./                                                 # ← 再复制源码
  RUN dotnet publish Blog.WebApi/Blog.WebApi.csproj -c Release --no-restore -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime    # 阶段 2：约 220MB
  ARG VERSION / GIT_SHA / BUILD_TIME                    # ⚠️ ARG 必须在使用的阶段重新声明
  ENV ASPNETCORE_ENVIRONMENT=Production ASPNETCORE_HTTP_PORTS=8080 ...
  RUN apt-get install -y curl                           # 只为 HEALTHCHECK（官方镜像不含 curl）
  COPY --from=build /app/publish ./
  RUN mkdir -p /app/media /app/logs && printf ... > /app/version && chown -R app:app /app
  USER app                                              # UID 1654，绝不用 root 跑应用
  HEALTHCHECK CMD curl -fsS http://127.0.0.1:8080/health
  ENTRYPOINT ["dotnet", "Blog.WebApi.dll"]
```

四个要点：

1. **分层构建**：`.csproj` 很少变，源码几乎每次都变。把 `COPY . .` 放在 `restore` 之前，
   会导致"每次改一行 C# 都要重新下载全部 NuGet 包"。现在的顺序让依赖层在清单没变时命中缓存。
2. **版本号必须走 build-arg**：本镜像的构建上下文只 `COPY` 了 `Blog.Backend/`，**`.git` 根本不在镜像里**，
   MSBuild 的 `SourceRevisionId` 拿不到任何东西。
3. **ARG 的坑**：只在 build 阶段声明的 `ARG`，runtime 阶段看不到，必须在 runtime 阶段重新声明一次。
4. **非 root**：`chown` 必须在 `USER app` **之前**执行。一旦被拿下，攻击者在容器内不是 root。

**`deploy/nginx.Dockerfile`**（前端构建 → Nginx）

```dockerfile
FROM node:24-bookworm-slim AS build     # glibc 而不是 alpine(musl)
  COPY package.json package-lock.json ./
  RUN npm ci                            # 严格按 lock 安装；不能加 --omit=dev（vite/vue-tsc 在 devDeps 里）
  COPY Blog.FrontEnd/ ./
  RUN npm run build

FROM nginx:1.29-alpine                   # 只剩 dist/，node_modules 与源码不进最终镜像
  COPY deploy/nginx.conf /etc/nginx/conf.d/default.conf
  COPY --from=build /src/dist /usr/share/nginx/html
```

选 `bookworm-slim` 而不是 `alpine` 的原因：依赖里有带**原生二进制**的包
（rolldown、lightningcss），npm 按平台安装对应实现；glibc 是最稳妥的默认选择，
与开发机（Windows）行为差异最小。

**PG 与 Redis 都只拉不建**。PG 用社区镜像 `mixdeve/postgres-zhparser:18`
（官方镜像没有 zhparser；为什么选它见 `deploy/README.md` §1）。
它**浮动在大版本 tag 上**（上游只发 `18` 这类 tag）是已知取舍 ——
说明与改用 digest 锁死的写法在 `docker-compose.yml` 的 `pgsql.image` 注释里。

### 4.3 compose 编排要点

```yaml
name: blog
services:
  pgsql:   image: ${POSTGRES_IMAGE:-mixdeve/postgres-zhparser:18}
           volumes: [pgdata:/var/lib/postgresql]        # ⚠️ 不是 /var/lib/postgresql/data
           healthcheck: pg_isready
  redis:   image: redis:7.4.11-alpine                   # ⚠️ 版本钉到 patch 位
  webapi:  build: deploy/webapi.Dockerfile
           depends_on: {pgsql: service_healthy, redis: service_healthy}
           volumes: [media:/app/media, logs:/app/logs]
           deploy.resources.limits.memory: 768m         # 只限 webapi
  nginx:   build: deploy/nginx.Dockerfile
           depends_on: {webapi: service_healthy}
           ports: ["${HTTP_PORT:-8080}:80"]
```

几处**不是调优、而是必需**的配置：

- **`condition: service_healthy` 而不是默认的 `service_started`**：
  "容器启动了" ≠ "数据库能连了"。应用启动时会执行数据库迁移，PG 没就绪就直接崩——
  这是 CI/部署里最常见的随机失败来源。
- **PG 卷挂载点是 `/var/lib/postgresql`**，不是 `/var/lib/postgresql/data`。
  PG18 的 `PGDATA` 实际是 `/var/lib/postgresql/18/docker`，写错会让容器以为数据目录为空而
  **重新初始化**——表现为"数据看起来丢了"。
- **Redis 版本钉到 patch 位**（`7.4.11-alpine` 而不是 `7-alpine`）。
  浮动 tag 会在上游重新推送时指向另一次构建，于是本地测过的 Redis 和服务器上跑的可能不是同一个东西，
  **而这一点从任何日志里都看不出来**。写死后：本地 = CI = 服务器。
  （PG 镜像做不到这一点，上游只发 `18` 这类大版本 tag，这是一个已知取舍。）
- **webapi 的内存上限 768m**：不加时 .NET 按**宿主机总内存**算 GC 堆硬上限（默认 75%），
  2G 机器上就是 1.5GB，一次大图上传或大响应就可能涨到那个量级，把 pgsql 挤到被内核 OOM Kill
  （表现为"博客突然 502，PG 容器重启过"）。加上限后 .NET 改按 768MB 算（GC 上限约 576MB）。
  实测空载只有 145MB。**只限 webapi**：它是唯一会贪心增长的进程，PG 的 `shared_buffers` 是启动时定死的。
- **`cpus` 刻意不设**：2 核机器上掐 CPU 配额会引入节流，压测时看到的就不是真实瓶颈了。

`docker-compose.prod.yml` 是服务器专用覆盖，只做一件事：把 `webapi` / `nginx` 的镜像改成从
GHCR 拉（`pull_policy: missing`，配合 `deploy.sh` 里"先 pull 再 up"的顺序，绝不会尝试构建）。
两个变量用 `:?` 强制要求存在——缺失时直接报错退出，而不是悄悄回退到本机构建的
`blog-webapi:local`（那会让你以为部署成功了，其实跑的是旧镜像）。

### 4.4 nginx.conf 逐段说明

| 段 | 关键点 |
|---|---|
| `upstream blog_api` | `server webapi:8080; keepalive 32;` 与后端保持长连接，避免每个请求重新握手 |
| `set_real_ip_from` | 信任 `127.0.0.1` 与 `172.16.0.0/12`（Docker 网桥默认网段）。宿主机 Caddy 反代进来之后，容器看到的对端会变成宿主机，靠这段把真实 IP 还原回去 |
| `client_max_body_size 12m` | **Nginx 默认上限只有 1MiB**。不设这行，大于 1MB 的图片会被 Nginx 直接拦成 413，**请求根本到不了后端**，后端日志里什么都看不到——会让人误以为是前端问题 |
| 安全响应头 | `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: strict-origin-when-cross-origin`。⚠️ `add_header` 只在**当前层级没有** `add_header` 时继承，所以每个自定义 location 里都重复了一遍 |
| `gzip` | 只压 css/js/json/svg，`gzip_min_length 1024` |
| `location /api/` | `proxy_http_version 1.1` + `Connection ""`（长连接必需）；**`X-Forwarded-For $remote_addr` 覆盖**而不是追加（见 3.4 的越权绕过坑）；`X-Forwarded-Proto $scheme` |
| `location = /health` | 也走反代，便于从外部探活；`access_log off`；同样覆盖 XFF |
| `location /assets/` | `expires 1y` + `immutable`。Vite 产出的是 `index-<hash>.js`，内容一变文件名就变，可以放心长缓存 |
| `location = /index.html` | `expires -1`（不缓存）。它引用的是带 hash 的资源，每次构建都会变；一旦被缓存，用户会一直加载**旧版本前端**，而旧前端可能调用已经改过的 API |
| `location /` | `try_files $uri $uri/ /index.html` —— SPA history fallback，缺了它 `/post/<id>` 刷新就 404 |
| `listen [::]:80` | 同时监听 IPv6。缺了它，容器内的健康检查（`localhost` 优先解析成 `[::1]`）会永远失败，而从宿主机访问一切正常 |

### 4.5 CI/CD 流水线

`.github/workflows/ci.yml`，六个作业，是一条链：

```
push / PR ──┬─ hygiene    行尾检查（秒级失败，期望它最先红）
            ├─ frontend   vue-tsc -b --force + vite build
            ├─ backend    格式 → 编译 → 全部测试（真实 PG）→ 迁移链 + 分词映射 → 覆盖率
            └─ security   NuGet(含传递依赖) + npm 漏洞扫描   ← 只报告不阻断，不在链上
                     │
   合并进 main 或 推 v* tag
                     ▼
              publish   三个检查全绿 → 构建两个镜像推 GHCR（tag = commit sha）
                     │
              推 v* tag（唯一上线入口）
                     ▼
              deploy    同步 compose/脚本 → SSH deploy.sh update → 从公网核对 sha
```

**为什么把"合并"和"上线"拆开**：合并是日常高频动作，而 deploy 会重建容器、中断线上几十秒。
让"改代码"和"上线"共用同一个动作，等于每次合并都在赌测试覆盖不到的地方。现在两道闸门分工明确：

- 测试全绿 → 允许产生**制品**（publish，任何人合并都会发生）；
- 你要上线 → 推一个**版本 tag**（deploy，一次发布才发生一次）。

于是"CI 绿 → 线上就是它"仍然是自动的（没有手工登录服务器这一步），但**要不要上线由人决定**。

`workflow_dispatch`（手动触发）**只跑四个检查作业**：手动触发时 ref 可以是任意分支，
让它发布或部署等于"把功能分支发到生产"。

`concurrency` 的设置也有讲究：PR 与 main 可以 `cancel-in-progress`（省额度，
代价是 **main 不保证每个提交都有镜像**，要确定的镜像就发版），
**但 `v*` tag 一律排队**——取消一个正在部署的运行会把线上留在半更新状态，且新旧两次部署会互相抢。
`deploy` 作业自己还有 `concurrency: deploy-production` + `cancel-in-progress: false`：
两次并发 update 会互相抢，先启动的那次若最后完成，线上就被退回旧 sha（且它同样是"成功"的）。

#### 几处刻意的"防假绿"

| 措施 | 防的是什么 |
|---|---|
| 解析 `.trx` 报告，`total == 0` 判失败 | `dotnet test` 在"一个测试都没发现"时**也返回退出码 0**。路径写错、过滤器写错、测试没被编译进产物，都会让流水线变绿而实际什么都没验证 |
| 覆盖率报告没产出就判失败 | `--settings` 丢失/改名时收集器静默失效，流水线不会因此变红 |
| 漏洞扫描输出里必须有 `vulnerab` 字样 | 扫描命令本身失败（网络不通、还原没完成）和"没有漏洞"是两件事，不能混为一谈 |
| 部署后轮询公网 `/api/version` 直到看到这次 sha（60 秒，10 次） | "SSH 命令退出码 0" ≠ "公网真的在跑这一版"。Caddy / Nginx / 应用缓存任何一层没换，上一步都看不出来 |
| `assert_image`（`docker inspect` 断言容器**实际**跑的镜像名） | compose 可能因"配置没变"而不重建容器，只看命令退出码会被骗过去 |

#### 版本号与镜像 tag

| 触发 | VERSION | `:latest` |
|---|---|---|
| 推 `v*` tag | tag 名（如 `v0.1.0`） | **移动** |
| 合并进 main | `v0.0.0-main.<短sha>` | **不动** |

两个镜像（webapi / nginx）用**完全同一套 tag 规则**，这样"前后端同版本"是一个可以直接观察的事实。
tag 里必须有**裸 sha**（`type=raw,value=<sha>`，不是 `type=sha` 的 `sha-` 前缀形式）——
`deploy.sh update` 就是拿 `:<sha>` 去 pull 的，两个镜像 tag 形式不一致会让整个更新失败（线上实测踩过）。

`:latest` 只在打 tag 发布时移动，它才等于"最新正式版"这个可靠含义；
日常 main 构建仍然可用不可变的 `:<sha>` 部署，能力没有损失。

#### 部署用的 secrets / vars

```
secrets.DEPLOY_HOST / DEPLOY_USER / DEPLOY_SSH_KEY
secrets.DEPLOY_HOST_FINGERPRINT   # 可选加固：填了就校验主机密钥（防中间人），不填则退回"不校验"
vars.SITE_URL                     # 可选，默认 https://www.kkynet.site
```

`GITHUB_TOKEN` 用于推 GHCR（`permissions: packages: write`），
**CI 全局 env 里没有任何密钥**——集成测试夹具强制 `UseEnvironment("Development")`，
读的是 `appsettings.Development.json` 里的开发签名密钥。密钥注入是 CD 阶段才需要的事。

### 4.6 首次部署 / 更新 / 回滚 / HTTPS

`tools/deploy/deploy.sh` 是部署的唯一入口，五个命令：本地 `build`，
服务器 `init` / `update` / `https` / `status`。完整流程见 `tools/deploy/README.md`，这里只记要点。

**首次部署**（走本地打包，因为服务器上还没有 compose 与 `.env`）：

```bash
bash tools/deploy/deploy.sh build all     # 打包 webapi + nginx + PG + Redis 镜像
scp dist-images/blog-images-*.tar.gz docker-compose.yml docker-compose.prod.yml user@host:/opt/blog/
ssh user@host 'mkdir -p /opt/blog/tools/deploy'
scp tools/deploy/deploy.sh user@host:/opt/blog/tools/deploy/     # ⚠️ 路径不能变，CI 就在那里找它
ssh user@host
cd /opt/blog && IMAGE_PREFIX=ghcr.io/<owner>/<repo> bash tools/deploy/deploy.sh init blog-images-*.tar.gz blog.example.com
```

`init` 依次做四件事：

1. **`setup_swap`**：内存 ≤ 3GB 且 swap < 1GB 时自动建 2GB swap 并写 `/etc/fstab`，
   同时把 `vm.swappiness` 设成 10。2G 机器上没有 swap，PG 做 VACUUM / 大排序会被内核 OOM Kill。
2. **`write_env`**：`openssl rand -base64 48` 生成 JWT 密钥、`rand -base64 24` 生成 PG 密码，
   `umask 077` + `chmod 600` 写 `.env`（密钥在服务器现生成，从不经过仓库）。
   默认 `HTTP_PORT=127.0.0.1:8080`——只监听回环，对外由 Caddy 终结 TLS。
3. **`docker load` → `compose up -d` → `wait_health`**（最多 120 秒，失败时打印 webapi 最后 40 行日志）
   → **`assert_memory_limit`**（`docker inspect` 读 `HostConfig.Memory`，为 0 就报错：
   "配置里写了 ≠ 内核真的限制了"）。
4. **`cmd_https`**：装 Caddy（从 cloudsmith 源）→ 写 `/etc/caddy/Caddyfile` →
   `caddy validate` → `systemctl reload`。

跑完必须立刻做两件事：**改掉种子管理员密码**（`admin@example.com / Admin@12345` 是公开的，
改完要用旧密码再登录一次确认失败），以及去 GitHub Packages 把两个 package 的 visibility
改成 **public**（否则服务器拉不动镜像）。

**日常更新**（现在由 CI 自动执行）：

```bash
bash tools/deploy/deploy.sh update <完整sha>            # 只接受完整 sha，短 sha 在 registry 里没有 tag
bash tools/deploy/deploy.sh update <完整sha> --check    # 只拉不切：不改 .env、不重建容器
```

`update` 的顺序是刻意的：

```
校验 .env / compose / IMAGE_PREFIX（CHANGE_ME 直接报错）
  → docker compose pull webapi nginx        ← 先拉，失败时栈还停在旧版本
  → 写 .env 的 WEBAPI_IMAGE / NGINX_IMAGE   ← 拉成功才改
  → docker compose up -d webapi nginx
  → docker compose restart nginx            ← ⚠️ 否则 502（见下）
  → wait_health
  → assert_image webapi / nginx             ← 断言容器实际在跑这个镜像
  → 打印 curl /api/version 的结果
```

那个 `restart nginx` 是必需的：**Nginx 在启动时解析了上游主机名并缓存了 IP**，
webapi 容器重建后 IP 可能变化，而 Nginx 不会自动重新解析——表现为更新后 502。

**回滚** = 用旧 sha 再部署一次（镜像 tag 不可变，所以这总是可行的）：

```bash
bash tools/deploy/deploy.sh update <上一个 sha>
```

⚠️ **只回滚应用，不回滚数据库结构**。应用启动时会自动跑 EF 迁移，而旧镜像不会把表结构改回去。
本项目**没有备份功能**（个人项目，刻意不做），表结构变更只能自己想清楚再上。

**HTTPS / 换域名**：`deploy.sh https <域名> [邮箱]`。前置条件是域名的 A 记录已指向这台机器
（Let's Encrypt 要回连验证），且防火墙与云安全组放行 **80 / 443**。

#### 改了什么要做什么

| 改了什么 | 动作 |
|---|---|
| 后端 / 前端 / Dockerfile / nginx.conf | 合并后**不会自动上线**，要上线就推一个 `v*` tag（或手工 `update <sha>`） |
| `docker-compose*.yml`、`tools/deploy/deploy.sh` | 走 CI 时无需动作（每次自动部署前会覆盖同步）；手工部署要自己 `scp` |
| compose 里 `pgsql:` / `redis:` 的 `image:` 行 | 服务器执行 `docker compose pull pgsql redis && docker compose up -d pgsql redis`（数据在命名卷里，不会丢） |

> CI 同步 compose 与脚本时**绝不设置 `rm`**——那会把服务器上的 `.env` 一起删掉
> （它不在仓库里，删了只能重新生成密钥）。

### 测试夹具的几个关键设计

- **每次运行新建随机测试库** `{原库名}_test_{8位随机}`，结束时 `DROP DATABASE ... WITH FORCE`。
  不污染开发库，也不会与其他测试运行冲突。
- **Redis 换库而不是关掉**：连接串加上 `defaultDatabase={1..15}` 随机 index。
  为什么必须隔离——测试库每次都是新的，但**种子账号的 Id 是写死的**，
  而缓存 key 由 Id 决定（`blog:auth:user:v1:{id}`）。上一轮被注销测试提升过 `TokenVersion`，
  缓存里留着旧快照，这一轮读到时会被判为"TokenVersion 不匹配"，种子 admin 的 token 全部 401。
  实测踩过：**整轮 220 个用例里 52 个连环失败**，而单跑某个用例却是绿的。
  选"换库"而不是"关缓存"，是为了让集成测试仍然覆盖 Redis 实现本身（降级、哨兵、锁）。
- **限流关掉**（`RateLimit:Enabled=false`）：集成测试连发请求会远超阈值而误报 429，
  更麻烦的是限流桶存在 Redis 里、是跨运行共享的外部状态。限流本身另有专门验证。
- **连接串来自 `BLOG_CONNECTION` 环境变量**，回退到 `appsettings.Development.json`。
  CI 只需设一次，也不会出现两处凭证悄悄漂移。
- **不做任何"预建 chinese 配置"的准备**。历史上确实需要（迁移把 `AddColumn<SearchVector>`
  排在创建配置的 SQL 之前，干净库跑迁移必定失败，报 `42704: text search configuration "chinese" does not exist`），
  当时的应对是在夹具里先建好配置绕过去——那等于**把缺陷掩盖在测试里**。
  现在迁移自己会建扩展与配置，所以夹具不需要任何前置准备，
  **集成测试是在一个完全干净的库上跑迁移的，这本身就是那个缺口的回归防护**。

### 覆盖率口径

`coverage.runsettings` 排除 EF 迁移、模型快照与 `obj/` 下的源生成代码。这不是为了好看，是**先让数字有意义**：

```
未排除：行 81.8% / 分支 40.4%   Blog.Infrastructure 91.8%   ← 虚假的
排除后：行 70.2% / 分支 49.8%   Blog.Infrastructure 75.8%   ← 真实基线
```

代码一行没改，行覆盖率降了 11.6 个百分点，分支覆盖率反而升了 9.4 个百分点——
变的只是统计口径。那个 91.8% 里 73% 的行数来自五个生成文件（迁移 + 快照），
它们"被执行过"（集成测试一跑就会执行），但**一行都不代表被测过**。

**不对总量设阈值**。理由写在 CI 的作业摘要里：阈值只会逼人写不 `assert` 的测试来凑数。

## 6. 前端概览

只写对理解全链路有用的部分。

### 结构

```
src/api/*.ts        每个后端资源一个模块，全部走 http.ts
src/stores/         Pinia：auth（登录态）/ app（theme + search 两个 store）/ site（站点配置）
src/router/         vue-router，嵌套布局 + meta 权限
src/layouts/        DefaultLayout（公开站）/ AuthorLayout（/me）/ AdminLayout（/admin）
src/views/          页面；admin/ 与 me/ 是后台与作者区
src/utils/markdown.ts   marked + DOMPurify
src/utils/media.ts      上传框的 accept 白名单（刻意不含 svg）
src/components/     按领域分子目录，含 skeleton 骨架屏
```

依赖极简：**没有 UI 组件库、没有 axios、没有富文本编辑器、没有代码高亮库**。
表格、分页器、模态框、骨架屏、图标（内联 SVG path）全是手写的。
代价是加图标要手抄 path，收益是没有一整套需要跟着升级的组件依赖。

### 请求层（`src/api/http.ts`）

- `BASE` 来自 `import.meta.env.VITE_API_BASE`，**开发和生产都留空**：
  开发走 Vite 代理（`/api` → `localhost:5131`），生产走 Nginx 反代，
  两边都是**同源**，完全不会触发 CORS。
- token 的读取方式由 `main.ts` 通过 `configureHttp({getToken, onUnauthorized})` 注入，
  避免 http 层直接依赖 store / router 造成循环引用。
- 统一响应体在这里被解构：`code !== 0` 就抛 `ApiError(code, message)`；
  非 JSON 响应（网关 502、裸 404）按 HTTP 状态码兜底，文案中性化。
- `4010` 会触发 `onUnauthorized()`（清登录态 + 跳登录页）；登录接口本身的 401 由调用方判断。
- 上传用 `FormData`，**不能预设 `Content-Type: application/json`**，浏览器要自己生成 multipart boundary。

### 登录态（`src/stores/auth.ts`）

localStorage 三个键：`blog-auth-token` / `blog-auth-user` / `blog-auth-expires`。

存 localStorage 是一个明确的权衡：写起来简单、刷新不丢，代价是任何 XSS 都能读到它。
所以前端的 XSS 防线（DOMPurify）不是可选项。缓解措施是：

- `isAuthenticated` **必须叠加 `!isExpired`**（本地过期时间来自登录响应的 `expiresAt`），
  只看 `token && user` 会让过期 token 一直显示为已登录；
- 有 30 秒的轮询检查 token 是否到期，到期就登出；
- `restore()` 在启动/刷新时会向后端确认一次 `/api/auth/me`，
  这样能正确处理"token 没到期但账号已被停用/改密"的情况。

### 路由守卫（`src/router/index.ts`）

路由 meta 声明 `requiresAuth` 与 `roles`，`beforeEach` 统一判断。
`meta` 会沿匹配链合并（父路由的 `requiresAuth` 对子路由同样有效），所以不需要自己遍历 `to.matched`。
守卫只是**体验层**的把关，真正的权限在后端策略上——前端拦不住的请求，后端一律 401/403。

### Markdown 渲染（`src/utils/markdown.ts`）

`marked.parse`（同步模式，异步模式返回 Promise，`v-html` 拿不到字符串）→ `DOMPurify.sanitize`。

两处定制：

- `ADD_ATTR: ['id']`：DOMPurify 默认会剥掉 `id`，而标题锚点（目录跳转）依赖它；
- `FORBID_ATTR: ['style']` + 把 `<font>` 这类纯样式标签 **unwrap**（保留子节点）。

剥内联样式的理由很具体：富文本常常是从别的编辑器**粘贴**进来的，会夹带
`<font style="color:rgb(15,17,21)">`（近黑色）。亮色主题下看不出问题，
一切到暗色主题就是**黑底黑字**。根因不是 CSS 变量没适配（正文排版全用 `var(--text-*)`），
而是内联样式**优先级更高**，把主题覆盖掉了。顺带还堵掉一类问题：
内联样式本身就是 CSS 注入面，`background:url(//evil.com/track)` 可以不执行任何 JS 就做追踪像素。

### 构建

`npm run build` = `vue-tsc -b && vite build`（类型检查不过就不产出）。
`@` 别名指向 `src`。CSS 变量集中在 `styles/tokens.css`，全局样式在 `styles/global.css`。

几个和"全链路"有关的构建事实：

- **`build` 会因为一个没删干净的局部变量而失败** —— `tsconfig.app.json` 开了
  `noUnusedLocals` / `noUnusedParameters`，而 `vite dev` 完全不报。
- **`import.meta.env.*` 没有类型约束** —— 仓库里没有 `env.d.ts`，类型全靠 `types: ["vite/client"]`，
  所以 `VITE_API_BASE` 拼错不会编译报错，只会在运行时静默变成 `undefined`。
- **分包完全由路由懒加载驱动**：23 条路由的 `component` 全是 `() => import(...)`，
  没有 `manualChunks`，产物就是"每个页面一个 `xxx-<hash>.js` + 同名 css"。
- `参考设计规范/tokens-v2.css` 与 `src/styles/tokens.css` 是**逐字节相同的两份副本**
  （实现原样复制了设计交付），目前没有任何机制保证它们同步。
- 装了 `sass`，但 41 个 `<style scoped>` **没有一个带 `lang="scss"`**，
  `_tokens-v2.scss` 里的 mixin 也全未使用 —— 属于"预置但未启用"。

## 8. 代码里已知的问题与待办

这一节是"翻代码时顺手记下来的"，不是 roadmap。
每条都写清楚**是读码确认的、还是只是推断**，免得下次当成事实。

> **2026-10-10 状态**：8.1 的 ①②③④⑤⑥ 与 8.2 ① 都已修复（PR #62），
> 对应提交：① `0bd4929`、② `449174a`、③ `f4d59d2`、④ `794a315`、⑤ `27b1aeb`、⑥ `7c8bcc8`、8.2① `b29c910`。

### 8.1 已确认（读码可对照，有明确分歧点）

**① `PUT /api/users/{id}` 停用账号不会提升 `TokenVersion`**

`UserService.UpdateAsync` 里是这么写的：

```csharp
user.UpdateProfile(role, request.AuthorId, request.IsActive);  // 这个方法内部就写了 IsActive
user.SetActive(request.IsActive);                               // 值已相等 → 第一行就 return
```

`SetActive` 的第一行是 `if (IsActive == isActive) return;`，而 `UpdateProfile` 刚刚已经把
`IsActive` 赋成了同一个值，所以**必然提前返回，`TokenVersion` 不会 +1**。
对比专用端点 `DisableAsync`（直接 `SetActive(false)`）是正常的。

实际后果分两段看：

- **停用立即生效** ✅ —— `UpdateAsync` 末尾主动失效了认证缓存，下一个请求回源读到
  `IsActive = false`，中间件写入 `Inactive` 拒绝，401；
- **"旧 token 永久失效"不成立** ❌ —— 账号被**重新启用**后，停用前签发的 token 又变得可用（直到自然过期）。

而 `RequireResolvedUser` 那套机制的前提正是"凭据一旦作废就永久作废"，所以这里是实现与意图不符。
修法：把 `UpdateProfile` 拆成"不动 IsActive 的部分"，或者让 `UpdateAsync` 显式判断
`if (user.IsActive != request.IsActive) user.SetActive(request.IsActive);` 并自己处理 `TokenVersion`。

**② `TagService` 的更新/删除缺少 `version >= 1` 校验**

`TagsController` 的 `PUT` 用 `UpdateTagRequest(Name, Version)`、`DELETE` 用 `[FromQuery] int version`，
两者都有"没传就是 0"的默认值。而 `TagService.UpdateAsync` / `DeleteAsync` 直接把值传给仓储，
没有像 `CategoryService` / `PostService` / `UserService` / `AuthorService` / `CollectionService` /
`SiteService` 那样先 `ValidateVersion`。

`BaseRepository.ApplyOptimisticVersion` 在 `expectedVersion < 1` 时抛 `ArgumentOutOfRangeException`
→ 被全局中间件当未处理异常 → **500 + 5000**，而同类接口给的是 **400 + 4001「缺少合法的版本号」**。

也就是说：不带 `version` 调 `DELETE /api/tags/{id}` 会得到 500 而不是 400。
`OptimisticLockTests` 覆盖了 posts / categories / site config，**没有覆盖 tags**，
所以这个不一致一直没被测试抓住。

**③ `CollectionsController` 的 Admin 判定读的是 JWT claim，不是解析结果**

`IsAdmin() => User.IsInRole(nameof(UserRole.Admin))`，而用到它的两条路由
（`GET /api/collections?includeUnpublished=true`、`GET /api/collections/{slug}`）**没有 `[Authorize]`**，
因此不经过 `RequireResolvedUserRequirement`。

结果：一个**已注销**（或已被停用）但**尚未过期**的 Admin token，claims 里的 role 依然存在，
依然会被当作 Admin —— 能看到未发布专栏。其余写接口都挂了 `AdminOnly` 策略，不受影响。

修法：`IsAdmin()` 改成读 `ICurrentUser.IsAdmin`（或给这两条路由挂 `Authenticated` 策略后自行判断角色）。

**④ 归档缓存的版本号是硬编码的**

`CacheKeys.PostArchives = PostsPrefix + "archives:v1:-"`，而其它 key 走 `$"v{Version}"`。
将来把 `Version` 从 1 提到 2 时，归档缓存不会被整体失效。要么同步改这一行，要么接受
"旧 key 靠 TTL 自然消失"（30 分钟后也就没了，影响不大，但要知道）。

**⑤ 死代码 / 未被使用的定义**

| 定义 | 状态 |
|---|---|
| `CacheKeys.CollectionDetail(slug)` | **已删除**（`27b1aeb`）—— 专栏详情走 `CollectionService.GetBySlugAsync` 直查，本来就不缓存 |
| `IUnitOfWork.BeginTransactionAsync / CommitTransactionAsync / RollbackTransactionAsync` | **已删除**（`27b1aeb`）—— 连同随之变成死代码的 `UnitOfWork._transaction` / `Dispose()` / `: IDisposable` 一并删除 |

**⑥ 注释与实现/版本不一致的几处**

| 位置 | 问题 |
|---|---|
| `Directory.Build.props` | 暗示版本号经程序集元数据传给 `BuildInfoProvider`；实际 provider 只读环境变量（见 3.9） |
| `Blog.Tests.csproj` | 注释写"xUnit **v3** 的测试工程需要入口点"，但引用的包是 `xunit` **2.9.3** |
| `CategoryService.DeleteAsync` / `Post.cs` / `AuthorService` | 注释说"其下文章的 `CategoryId` / `AuthorId` 由 SetNull 置空"，但软删除是 UPDATE 不是 DELETE，FK 的 `ON DELETE SET NULL` 不会触发（见 8.2 ②） |
| `FieldLimits.cs` 类注释 | 仍以 `Posts.Summary` 曾是 `varchar(120)` 举例说明历史事故；现在的值是 **200**，别照抄 |
| `Program.cs` 的策略名常量 | 注释说常量是为了"避免魔法字符串不一致"，实际只有 `AuthController` 用了常量，其余控制器都写 `"AdminOnly"` / `"ContentWriter"` 字面量 |

**⑦ 契约上容易踩的点（不是 bug，但要知道）**

- **所有成功响应都是 200**，没有 201 / 204。
- `PostDetailDto.AuthorId` 是**非空** `Guid`，"无作者"用 `Guid.Empty` 表示而不是 null。
- `ApplyTagsAsync` 与 `ApplyCollectionsAsync` 的 null 语义**不同**：
  `TagIds = null` 等同空数组（会清空标签），`CollectionIds = null` 表示"本次不改动"、空数组才清空。
- **自动摘要 50 字 ≠ 字段上限 200**：`Post.SummaryLength = 50` 只控制自动截取长度，
  校验上限与列宽都是 200。
- **浏览量是最终一致**：读详情时先读缓存快照，再 `ExecuteUpdateAsync` 原子 +1，
  然后把缓存写成"快照 +1"并**重设 10 分钟 TTL**。DB 准确，缓存只是近似展示值；
  并发下自增可能被覆盖成较小的值。
- **慢查询阈值 500ms**，命中时会把**完整 SQL 文本**写进日志（参数都是参数化的，字面量风险低）。

### 8.2 静态推断（读码得出，**未实测**）

**① 更新文章时同步专栏可能撞主键**

`PostService.UpdateAsync` 调 `ApplyCollectionsAsync`，后者完全依赖 `post.CollectionLinks`：

```csharp
foreach (var link in post.CollectionLinks.Where(l => !ids.Contains(l.CollectionId)).ToList())
    post.CollectionLinks.Remove(link);

var existing = post.CollectionLinks.Select(l => l.CollectionId).ToHashSet();
foreach (var collection in collections.Where(c => !existing.Contains(c.Id)))
    post.CollectionLinks.Add(new PostCollection { ... });
```

但 `PostRepository.GetByIdAsync` **只 Include 了 `Tags`，没有 Include `CollectionLinks`**，
且没有开懒加载 —— 于是 `post.CollectionLinks` 是**空集合**：
第一个循环什么都不删，`existing` 为空，**所有请求里的 collectionId 都会被当成新增**。
如果其中某个专栏本来就关联着这篇文章，就会 INSERT 一行已存在的 `(PostId, CollectionId)`
→ 撞 `PK_PostCollections` → `DbUpdateException` → 500。

这不是凭空推测：`ICollectionRepository.cs` 的注释里已经记录了**同类事故**
（"触发 PK_PostCollections 唯一约束冲突（实测踩到过）"），所以 `CollectionService`
才改用 `GetWithPostsAsync`。而 Post 侧没有对应的"带连接集合"的查询方法，
`ApplyTagsAsync` 之所以安全，正是因为它依赖的 `Tags` 在仓储里被 Include 了。

**要验证/修的话**：给 `PostRepository.GetByIdAsync` 补 `.Include(p => p.CollectionLinks)`，
并加一条"把文章加入已有专栏后再保存"的集成测试。
测试目录里目前没有覆盖 `CollectionIds` 的用例。

**② 软删除不会触发外键的 `ON DELETE SET NULL`**

`BaseRepository.Remove` 是 `entity.Delete()` + `Update`，即发 **UPDATE** 而不是 DELETE。
所以模型里给 `Post.AuthorId` / `Post.CategoryId` / `Post.CreatedByUserId` 配的 SetNull
**对既有行不会生效**：文章仍然持有已软删分类/作者的 Id。

表现出来是"列里还有 Id，但名字变成 null"——因为查询投影走导航属性
（`p.Category != null ? p.Category.Name : null`），而全局查询过滤器 `!IsDeleted` 把软删的分类过滤掉了。
按 `CategoryId` 过滤本身仍然有效。

**③ 一处需要留意但当前无害的细节**

`Program.cs` 的 `UseStatusCodePages` 注释说它"必须在 `UseRouting` 之后"，
而代码里**没有显式调用 `UseRouting`** —— 靠的是 minimal hosting 在管线最前面自动插入。
行为正确，但读代码时不容易看出来，改管线顺序时要注意。

### 8.3 前端侧（同样偏"不一致"而不是 bug）

| 项 | 现状 |
|---|---|
| **HTTP 层没有超时** | `http.ts` 里没有 `AbortController` / `signal`，后端不响应时请求会一直挂着（页面停在 loading），只能靠 Nginx 的 `proxy_read_timeout 60s` 兜底 |
| **注释声称有 CSP，实际没有** | `stores/auth.ts` 的注释写"用短有效期 + CSP 补偿"，但 `index.html` 与 `nginx.conf` 里都没有 `Content-Security-Policy` 头（只有 nosniff / X-Frame-Options / Referrer-Policy） |
| **专栏封面还是自由文本 URL** | 头像 / 文章封面 / 站点 Logo / 首屏背景图都已经改成"只能上传"，只有 `AdminCollectionListView` 的封面是个 URL 输入框。服务端 `MediaPath` 白名单仍然拦得住，但策略不一致 |
| **`VITE_SITE_NAME` 是死配置** | `.env` 里定义了它，全仓无消费点；真实兜底是 5 处硬编码的 `"kky's blog"` |
| **Ctrl/Cmd+K 只在公开站有效** | 快捷键在 `main.ts` 全局注册，但 `<SearchModal>` 只挂在 `DefaultLayout` —— 在 `/admin/*` 与 `/me/*` 下会置位 `search.open` 却没有弹窗（状态还会残留到下次进公开页） |
| **NavBar 的"管理"入口不判角色** | 对匿名访客也可见，点了才被路由守卫重定向。无害但是条 UX 死路 |
| **`auth.verified` 只写不读** | 注释说它避免每次导航都请求 `/me`，实际读取点为 0（靠 `restore()` 只在启动跑一次） |
| **刷新页面后主动到期轮询不启动** | `scheduleExpiryWatch()` 只在 `setSession()`（登录）里调用；被动 401 那条防线仍然有效 |
| **首屏可能有一次主题跳变** | `apply()` 在 `app.mount()` 之前执行，而挂载要等 `/api/auth/me`；这中间 `<html>` 上还没有 `data-theme`，系统偏好亮色的用户会看到一次"亮 → 暗" |
| **`AdminAuthorListView` 的 version 兜底值有风险** | 编辑时从前端列表里 `items.find(...)?.version ?? 1` 取，缓存缺失时会用错的版本号发请求 → 4090 冲突 |
